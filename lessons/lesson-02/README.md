Краткий конспект разобранного. Каждая тема — объяснение в несколько строк и ссылка

```bash

```

## Работа над ошибками первого урока

> Файл: [`examples/00-errata.ts`](examples/00-errata.ts)

**Примитивов в JavaScript семь**, а не восемь: `string`, `number`, `bigint`,
`boolean`, `undefined`, `symbol`, `null`. `object` — не примитив, это всё остальное.
Восьмёрка берётся из другого: столько разных строк умеет вернуть `typeof`
(семь примитивов минус `null` плюс `'object'` плюс `'function'`).

**`typeof null === 'object'`** — историческая ошибка 1995 года, исправлять не стали.
Это про рантайм-оператор `typeof`; в TypeScript тип `null` — это `null`.

**`"strict": true` в tsconfig и `'use strict'` в JavaScript — разные вещи.**
Первое включает набор проверок **типов** (`noImplicitAny`, `strictNullChecks` и ещё
несколько) и работает только при компиляции. Второе — режим самого языка, работает
в рантайме. А `const` запрещает переприсваивание всегда, независимо от обоих.

**`tsc` не ставится глобально.** Глобальная установка означает, что у каждого своя
версия компилятора — ровно та проблема, ради которой в репозитории лежит `.nvmrc`.
В `wl-e2e` `typescript` лежит в `devDependencies` и вызывается как `yarn typecheck`.

**`Map` и `Set` — не массивы.** Самостоятельные встроенные объекты из ES2015,
не наследуются от `Array`: ни `push`, ни `pop`, ни индексов. У `Set` нет ключей —
`keys()` это псевдоним `values()`. Повторное добавление того же значения
игнорируется, ничего не удаляется.

**Forward declaration в JavaScript нет.** Нельзя объявить функцию сверху, а тело
написать через тысячу строк. Есть две другие вещи: *hoisting* — объявление
`function` поднимается, поэтому функцию можно вызвать выше по файлу; и
*перегрузки* — несколько сигнатур подряд, но реализация обязана идти вплотную.
Стрелочные функции не поднимаются вообще, это обычные `const`.

**`enum` в проекте не используется.** Во всём `wl-e2e` он один, и тот в замороженном
`explorer`. Наш стиль — union литералов, подробнее ниже.

## Типов в рантайме нет

> Файл: [`examples/01-runtime-types.ts`](examples/01-runtime-types.ts) ·
> [`examples/broken/01-type-error.ts`](examples/broken/01-type-error.ts)

Главное за оба урока. `type`, аннотации, `interface` стираются при сборке —
после транспиляции от них не остаётся ни байта. Тип это обещание компилятору,
а не проверка данных.

Отсюда два следствия.

**Тип ничего не знает о данных извне.** `JSON.parse(...) as Client` — не проверка,
а слово, которому компилятор поверил. Придёт строка вместо числа — TS будет считать
её числом, а умножение даст `NaN`. Данные из сети, из БД, со страницы нужно проверять
руками, через сужение (см. ниже).

**Тест может запуститься и даже пройти, имея ошибку типов.** Один и тот же файл:

```bash
node lessons/lesson-02/examples/broken/01-type-error.ts   # ✅ работает, печатает NaN
yarn typecheck:broken                                     # ❌ две ошибки типов
```

Node просто **вырезает** типы и запускает. Playwright их тоже не проверяет.
Ошибку ловит только `tsc`, то есть `yarn typecheck` — он входит в `yarn gate`.
Поэтому в корневом `tsconfig.json` проекта стоит `"noEmit": true`: компилятор там
ничего не собирает, он работает исключительно как валидатор.

> **Почему `.ts` вообще запускается через `node`?** Слово «скомпилировать» склеивает
> две операции: *избавиться* от типов (обязательно для запуска, Node умеет это сам
> с версии 22.18) и *проверить* их (для запуска не нужно, умеет только `tsc`).
> Node именно **стирает**: заменяет аннотации пробелами той же длины, поэтому номера
> строк в стектрейсе совпадают с исходником. Всё, что нельзя стереть, потому что оно
> порождает код (`enum`, `namespace`, параметры-свойства), Node не выполняет вовсе.

## Типы объектов

> Файл: [`examples/02-object-types.ts`](examples/02-object-types.ts)

Это 90% того, что пишется в файлах `C123456.helpers.ts`.

**Именованный тип.** Писать форму прямо в переменной можно только для одноразовых
объектов. Всё, что используется дважды, получает имя:

```ts
type SessionIdentity = { who: string; host: string; env: string };
```

Внутри фигурных скобок разделитель — точка с запятой. Справа от имени поля стоит
**тип**, а не значение: это описание формы, а не объект.

**Необязательные поля** помечаются `?`. Это не «можно не заполнять» — это «тип поля
теперь включает `undefined`», и компилятор заставит это обработать.

Важная деталь: если поле не указали, ключа в объекте **просто нет**.

```ts
const empty: LoginOpts = {};
Object.keys(empty);          // []
'forceFresh' in empty;       // false
empty.forceFresh;            // undefined  ← только чтение даёт undefined
```

Это не то же самое, что явно положенный `undefined` — там ключ есть. Разница видна
в `Object.keys`, спреде, `JSON.stringify` и проверке `in`.

**`readonly`** запрещает переприсваивать поле. Живёт только в компиляторе; рантайм-аналог —
`Object.freeze()`.

**Вложенность.** Пока вложенный объект нужен в одном месте, его можно описать прямо
внутри. Как только понадобился ещё где-то — выносится в свой тип. Для массивов
объектов тип объявляется на **один элемент**, а массив собирается уже на месте:
`items: BookingItem[]`.

**Функция как поле** записывается `имя: (параметры) => возвращаемыйТип`. При
присваивании типы параметров писать не нужно — TS берёт их из типа поля
(*контекстная типизация*). Отсюда общее правило: **аннотируются границы** —
объявления функций и типы, — а внутри работает вывод.

**`Record<K, V>`** описывает объект с произвольными ключами: `Record<string, string>`.
Старая запись `{ [key: string]: string }` работает так же, но `Record` короче.

**`type` или `interface`.** Для объектов взаимозаменяемы, отличий два: `interface`
можно доопределить повторным объявлением — поля сложатся, `type` так не умеет; зато
`type` описывает не только объекты, но и union, tuple, что угодно. **По умолчанию
пишем `type`** — одна конструкция на все случаи.

## Структурная типизация

> Файл: [`examples/03-structural-typing.ts`](examples/03-structural-typing.ts)

**TypeScript сверяет форму, а не имя типа.** Два одинаковых по форме типа с разными
именами взаимозаменяемы — в Java или C# это была бы ошибка.

Самое неочевидное место урока:

```ts
const withExtra = { x: 1, y: 2, z: 3 };
const a: Point = withExtra;              // ✅ проходит
const b: Point = { x: 1, y: 2, z: 3 };   // ❌ TS2353
```

Один и тот же объект: через переменную проходит, литералом на месте — нет.
Работают **две разные проверки**. Основная говорит «объект умеет всё, что требует
`Point`, значит подходит» — лишнее не мешает. Поверх неё есть **excess property
check**, и она срабатывает только на литералах, написанных прямо на месте.
Её единственная задача — ловить опечатки:

```ts
const cfg: WidgetConfig = { showPrice: true, showSpot: false };
// TS2561: 'showSpot' не существует. Имелось в виду 'showSpots'?
```

То же самое работает на аргументах функций — там ведь тоже литерал. Если лишнее поле
нужно осознанно, его кладут в переменную; но чаще это сигнал, что тип пора расширить.

## Дженерики

> Файл: [`examples/04-generics.ts`](examples/04-generics.ts)

**Угловые скобки передают тип в тип**, ровно как круглые передают значение в функцию.
`Array` — это «массив чего-то», и ему надо сказать, чего именно. Убрать слово `Array`
и оставить `<number>` нельзя — это как написать `(5)` вместо `f(5)`.

`Array<number>` и `number[]` — одно и то же. Для простых типов пишется короткая
форма, для составных — `Array<...>`, потому что `{ a: number }[]` читается хуже,
чем `Array<{ a: number }>`.

Параметров бывает сколько нужно: `Set<string>` — один, что лежит внутри;
`Map<string, number>` и `Record<string, boolean>` — два, ключ и значение.
А `Page` и `Locator` из `@playwright/test` — обычные типы без параметров.

**`Promise<T>`** — тот дженерик, который встречается чаще всех: так объявлена каждая
асинхронная функция. Читается «обещание вернуть `T` потом». `Promise<void>` —
«ничего не вернёт, но дождаться надо». `await` снимает обёртку: `Promise<string>`
превращается в `string`.

> Забыли `await` — в руках не значение, а объект `Promise`, и дальше всё разваливается
> непонятным образом. **Автоматически это не ловится:** правило
> `@typescript-eslint/no-floating-promises` существует, но в `wl-e2e` не включено,
> потому что требует линтинга с доступом к типам. Следить приходится самостоятельно.

**`Partial<T>`** делает все поля типа необязательными. Именно поэтому в тесте можно
написать `generateClientData({ firstName: 'Тест' })` и не перечислять остальные
двенадцать полей.

**Свой дженерик** нужен, чтобы тип прошёл сквозь функцию, а не потерялся:

```ts
function first<T>(items: T[]): T | undefined { return items[0]; }
first([1, 2, 3]);      // T = number → number | undefined
first(['Ann', 'Bob']); // T = string → string | undefined
```

`T` — имя-заглушка для типа, подставляется в момент вызова. Писать свои дженерики
придётся редко, читать чужие — постоянно.

## Union, литеральные типы и почему не enum

> Файл: [`examples/05-unions-narrowing.ts`](examples/05-unions-narrowing.ts) ·
> [`examples/broken/02-enum.ts`](examples/broken/02-enum.ts)

**Union** — вертикальная черта, читается «или»: `type Id = string | number`.
Работает с любыми типами; в проекте так объявлен, например,
`postLoginCheck?: string | Locator`.

**Литеральный тип** — не «строка», а одна конкретная строка. Сам по себе бесполезен,
полезен в union'е, и это основной рабочий инструмент:

```ts
type QuickContactSource = 'Email' | 'SMS' | 'Push';
```

Что это даёт: автокомплит прямо внутри кавычек, опечатка ловится в редакторе,
а при добавлении нового варианта компилятор показывает **все** места, где он
не обработан.

**Почему не `enum`.** Union — чисто типовая конструкция, после сборки от неё не
остаётся ничего. `enum` — одна из немногих конструкций TypeScript, которые существуют
в рантайме: превращается в настоящий объект и добавляет код. Node это показывает
буквально — он умеет только *стирать* типы, а `enum` стереть нельзя:

```bash
node lessons/lesson-02/examples/broken/02-enum.ts
# SyntaxError: TypeScript enum is not supported in strip-only mode
```

> Это **не** значит, что `enum` сломает тест. Playwright транспилирует через babel,
> полноценно, и `enum` под ним работает. «Мы не пишем enum» — конвенция проекта,
> а не техническое ограничение.

Вместо него — обычный объект с `as const`:

```ts
const SIZE = { S: 1, M: 2, L: 3 } as const;
type SizeName = keyof typeof SIZE;         // 'S' | 'M' | 'L'
type SizeValue = (typeof SIZE)[SizeName];  // 1 | 2 | 3
```

`as const` фиксирует значения — без него TS вывел бы просто `number`, и вся польза
исчезла бы. `keyof typeof` даёт union ключей, обращение по ключу — union значений.

Тот же приём на массиве, реальный код из `C154002.helpers.ts`:

```ts
const SETTINGS_SECTIONS = ['Lead form behavior', 'Form Settings', '...'] as const;
type SettingsSection = (typeof SETTINGS_SECTIONS)[number];
```

`[number]` означает «тип любого элемента по числовому индексу». Список написан один
раз: по нему бегает цикл и по нему же проверяются типы.

**`Record<Union, T>` — таблица, которую нельзя недозаполнить:**

```ts
const CLASS_BY_SOURCE: Record<QuickContactSource, string> = {
  Email: '...', SMS: '...', Push: '...',
};
```

Убрать строку — `TS2741: Property 'Push' is missing`. Добавить лишнюю — `TS2353`.
В этом и есть практический выигрыш union'ов: добавили `'Viber'` в тип — и
`yarn typecheck` сам привёл во все таблицы и `switch`, которые надо дополнить.

## Сужение и `never`

> Файл: [`examples/05-unions-narrowing.ts`](examples/05-unions-narrowing.ts)

Пока значение имеет тип `string | number`, ему доступно только то, что умеют **оба**.
Чтобы получить методы одного, надо доказать компилятору, какой он. Компилятор следит
за ветками сам — приведений писать не нужно.

Четыре способа, которые встречаются постоянно:

```ts
if (typeof id === 'string')      // по typeof
if (kind === 'admin')            // по литералу union'а
if (error instanceof Error)      // по instanceof — так читают catch
if (!login) throw new Error(...) // отсечение undefined: ниже login точно string
```

В `catch` тип всегда `unknown`, поэтому прочитать `.message` без проверки
`instanceof Error` компилятор не даст.

**`never`** — тип, у которого нет ни одного возможного значения. Если сужение отсекло
все варианты union'а, остаётся именно он. На этом строится проверка полноты:

```ts
default: {
  const exhaustive: never = source;
  throw new Error(`Неизвестный источник: ${String(exhaustive)}`);
}
```

В `default` исполнение не попадёт никогда. Строка существует ради того, чтобы
компилятор **привёл сюда**, когда union расширят.

## Разобрано по ходу

> Файл: [`examples/07-asked-during-lesson.ts`](examples/07-asked-during-lesson.ts)

**Шаблонные литералы** — обратные кавычки и подстановка `${выражение}`. Подстановка
происходит **в рантайме**, каждый раз заново, а не при компиляции: в скомпилированном
`.js` литерал остаётся дословно. Внутри `${}` можно любое выражение, результат всегда
приводится к строке — отсюда фокус с функцией без вызова, которая печатается целиком.

**Тернарный оператор** `условие ? если_true : если_false` — сокращённая запись
`if/else`, которая **возвращает значение**, поэтому её можно поставить прямо внутрь
выражения. Хорош, пока помещается в строку и не вложен в другой тернарник.

**`switch/case`** равнозначен цепочке `if/else if`, но читается лучше, когда одна
переменная сравнивается с набором значений, и его `default` явно показывает ветку
«ничего не подошло». Две ловушки: сравнение всегда строгое (`===`), и без `return`
или `break` выполнение «проваливается» в следующий `case`.

**Методы объекта** — функция внутри объекта. В типе описывается как обычное поле:
`checkItem: (id: string) => boolean`, либо второй формой `checkItem(id: string): boolean`.

**Дефолтные значения параметров** — `= значение` после параметра. Обычный JavaScript,
к типам отношения не имеет. Срабатывает только на `undefined`, но не на `null`.

## Не успели

`?.` и `??` — оптиональная цепочка и оператор нулевого слияния. Код уже лежит
в [`examples/06-optional-and-nullish.ts`](examples/06-optional-and-nullish.ts),
разбор — в начале третьего урока.

Коротко, чтобы не ждать: `?.` возвращает `undefined` вместо падения, если слева
`null`/`undefined`. `??` подставляет значение по умолчанию — но, в отличие от `||`,
срабатывает только на `null`/`undefined`, а не на любом falsy. Разница ловит
реальные баги: `spotsLeft || 10` при нуле свободных мест напечатает `10`.

## Словарь терминов

| Термин | Что означает |
|--------|--------------|
| **Транспиляция** | Перевод кода в код того же уровня: TS → JS. Компиляция в машинный код — другое |
| **Стирание типов** (type stripping) | То, что делает Node: убирает аннотации и запускает. Типы при этом не проверяются |
| **`noEmit`** | Режим, в котором `tsc` ничего не собирает и работает только как валидатор |
| **Аннотация** | Запись `имя: тип`. Существует только до сборки |
| **Вывод типов** (inference) | Компилятор определяет тип сам, без аннотации |
| **Контекстная типизация** | Частный случай вывода: тип параметра берётся из типа, в который его присваивают |
| **Литеральный тип** | Тип из одного конкретного значения: `'Email'`, а не `string` |
| **Union** | Тип «или то, или это»: `string \| number` |
| **Сужение** (narrowing) | Доказательство компилятору, какой именно тип из union'а сейчас в руках |
| **Проверка полноты** (exhaustiveness) | Приём с `never`, заставляющий обработать все варианты union'а |
| **Дженерик** | Тип с параметром: `Array<T>`, `Promise<T>`, `Record<K, V>` |
| **Параметр типа** | То, что стоит в угловых скобках. `T` — просто имя-заглушка |
| **Структурная типизация** | Сверка по форме, а не по имени типа |
| **Excess property check** | Дополнительная проверка на лишние поля, работает только на литералах |
| **`as const`** | Фиксирует значения, не давая расширить их до `string`/`number` |
| **`keyof`** | Union ключей типа |
| **`typeof` в позиции типа** | Взять тип существующего значения (не путать с рантайм-оператором) |
| **Модуль против скрипта** | Файл с `import`/`export` — модуль, имена локальные. Без них — глобальный скрипт |
