Материалов урока 7 нет, а запись его есть. Ниже — то, что в ней прозвучало неверно.

### Очереди: FIFO, и микрозадачи — до дна после каждой задачи

Внутри каждой очереди порядок — кто раньше встал, тот раньше выполнится
(FIFO); очередь — не стек. Микрозадачи не опрашиваются по таймеру: после
каждой макрозадачи очередь микрозадач разгребается до конца, включая
поставленные по ходу. Макрозадачи берутся **по одной**.

```ts
setTimeout(() => {
  console.log('4) макро 1');
  void Promise.resolve().then(() => console.log('5) микро из макро 1'));
});
setTimeout(() => console.log('6) макро 2'));
void Promise.resolve().then(() => {
  console.log('1) микро: первая');
  void Promise.resolve().then(() => console.log('3) микро, поставленная из первой'));
});
void Promise.resolve().then(() => console.log('2) микро: вторая'));
```

Вывод (`node` на файле с этим кодом):

```
1) микро: первая
2) микро: вторая
3) микро, поставленная из первой
4) макро 1
5) микро из макро 1
6) макро 2
```

И цикл событий — часть среды, а не движка: в Node это библиотека libuv
(документация Node.js, «The Node.js Event Loop»), в браузере — сам браузер.
V8 только выполняет JavaScript. Подробно про очереди —
[урок 5](../lesson-05/README.md#очереди-и-микрозадачи).

### Поиск только что созданного клиента — не «5 минут»

Правило T10 в `wl-e2e/RULES.md`: поиск клиентов в бэк-офисе видит новую
запись через **0–25 с** (переиндексация), а отрицательный ответ кэширует
на **~180 с**. Поэтому «создать, потом найти поиском» само себя ломает
на три минуты. Созданного клиента открывают по `uid`:
`createClient` возвращает его, а `/rs/profile.html?uid=<uid>` открывается
сразу. Цифры и замеры — `UI-PATTERNS.md` §9.10.1.

## Уточнения к занятию

Одиннадцать мест, где на занятии прозвучала неточность. Всё проверено запуском —
командами, `man git-gc` и настоящим прогоном; первые шесть разобраны в примерах.

### 1. `git bisect` называет ПЕРВЫЙ СЛОМАННЫЙ коммит

Не «последний правильный». Ответ у команды ровно один и выглядит так:

```
65ca99b… is the first bad commit
```

А строки `Bisecting: 2 revisions left to test after this` и следующая за ней
`[sha] сообщение` — это не ответ: так git докладывает, на какой коммит он встал
посередине диапазона, чтобы его проверить. Их за занятие печатается несколько,
и последняя из них выглядит убедительно похожей на результат.

Разница на один коммит меняет всё: сломавшая правка и её автор — в том
коммите, который назван `first bad`, а не в предыдущем. Разбор с полным
выводом — [`05-archeology.sh`](examples/05-archeology.sh).

### 2. Без `-m` открывается nano, а не vim — и выходят из них по-разному

`Ctrl+O` и `Ctrl+X` — клавиши **nano**. В vim это `Esc`, потом `:wq`.
На Ubuntu системный редактор по умолчанию как раз nano; на других системах
может открыться другой. Какой именно — покажет `git var GIT_EDITOR`.

Файл, который при этом редактируется, называется `.git/COMMIT_EDITMSG`.

Чтобы вместо обоих открывался VS Code:

```bash
git config --global core.editor "code --wait"
git var GIT_EDITOR        # проверять надо ЭТИМ, а не git config --get
```

Почему именно `git var`: git не проверяет имена ключей. Опечатка в названии
(`core.editoer` вместо `core.editor`) не вызывает никакой ошибки — настройки
просто не существует, а git молча берёт редактор по умолчанию. Подробно —
[`08-bash-and-editor.sh`](examples/08-bash-and-editor.sh).

### 3. Коммит в `detached HEAD` не «улетает в никуда»

Он валидный. Просто на него не ссылается ни одна ветка, поэтому `git log`
его не показывает. Достаётся из `reflog` и возвращается одной командой:

```bash
git reflog | head -3
git branch rescue <sha>          # или git switch -c rescue <sha>
```

Запись `reflog` о таком коммите живёт по умолчанию 30 дней. Опасность не в том, что
коммит пропадёт, а в том, что вы про него забудете. Живая проверка —
[`03-branches-and-detached-head.sh`](examples/03-branches-and-detached-head.sh).

### 4. `reflog` не вечный

Он не «неудаляемый неочищаемый журнал». Значения по умолчанию (`man git-gc`):

| Настройка | Умолчание | Про что |
|---|---:|---|
| `gc.reflogExpire` | **90 дней** | записи, достижимые из вершины ветки |
| `gc.reflogExpireUnreachable` | **30 дней** | всё остальное: detached-коммиты, снесённое `reset` |

Сеть безопасности есть, но не бесконечная.

### 5. `git log -G` ищет по тексту дифа, а не по содержимому файла

Коммит, где строка в файле есть, но диф её не трогает, командой `-G` не
находится. Проверка на трёх коммитах — в [`05-archeology.sh`](examples/05-archeology.sh):
`-G 'Book'` возвращает два коммита из трёх.

Коротко: **оба ищут в дифе**. `-S` считает число вхождений, `-G` матчит
регуляркой текст дифа.

### 6. В дифе `-1/+1` — это не «удалился перевод строки»

У git нет понятия «изменённая строка». Любая правка внутри строки — это
удаление старой строки и добавление новой, отсюда всегда `1 insertion(+),
1 deletion(-)`.

А если строки в дифе неожиданно склеились — смотрите на маркер
`\ No newline at end of file`: файл кончался без перевода строки, и дописанное
приклеилось к последней. Целиком тема разобрана ниже, в [«Как читать дифф»](#как-читать-дифф).

### 7. `git commit -am` берёт только отслеживаемые файлы

Это не то же самое, что `git add .` плюс `git commit -m`: `-a` берёт только
**уже отслеживаемые** файлы. Новый файл в такой коммит не попадёт
и останется `??`. А `git commit -m` сам не индексирует ничего:
пустой индекс — нет коммита. Если «`-m` закоммитил всё подряд», причина
в Smart Commit у кнопки VS Code — разбор в
[`08-bash-and-editor.sh`](examples/08-bash-and-editor.sh).

### 8. `git pull` не перезапишет незакоммиченное

Если чужие коммиты трогают файл, который вы правите и не закоммитили,
`pull` откажется целиком:

```
error: Your local changes to the following files would be overwritten by merge:
	f.txt
Please commit your changes or stash them before you merge.
Aborting
```

Файл остаётся как был. `stash` нужен не для защиты от перезаписи,
а чтобы `pull` вообще прошёл.

### 9. `reset --hard` не трогает новые неотслеживаемые файлы

Он возвращает к коммиту то, что git знает: индекс и отслеживаемые файлы.
Новый файл, ни разу не добавленный в индекс, после `git reset --hard`
остаётся в папке. Стирает его только `git clean -f` — и тогда уже
безвозвратно.

### 10. `code -r` — не «рекурсивно»

`code .` открывает текущую папку в VS Code со всеми подпапками и так.
`-r` — это `--reuse-window`: открыть в уже открытом окне, а не в новом.

### 11. Git хранит снимки, а не изменения

Коммит ссылается на `tree`, а `tree` — на **полное** содержимое каждого
файла:

```bash
git cat-file -p 'HEAD^{tree}'      # 100644 blob c46495d…	suites.txt
git cat-file -p c46495d            # widgets / monolith — весь файл, не разница
```

Копии при этом не плодятся: у одинакового содержимого один и тот же SHA,
и неизменившийся файл просто переиспользуется. Дифф git вычисляет тогда,
когда вы его просите.

## Три дерева

Пример: [`01-three-trees.sh`](examples/01-three-trees.sh)

Главное, чего нет в других системах контроля версий, — **индекс**, промежуточный
слой между вашей папкой и историей.

| Слой | Что это | Как посмотреть |
|---|---|---|
| **Рабочее дерево** | файлы, которые вы видите в папке и правите редактором | обычный `ls`, `cat` |
| **Индекс** (staging area) | черновик следующего коммита | `git status --short`, `git diff --cached` |
| **Коммит** | снимок, сохранённый навсегда: автор, дата, ссылка на предыдущий | `git log`, `git show` |

Команды, которые двигают файл между слоями:

```bash
git add ФАЙЛ            # рабочее дерево → индекс
git commit -m "текст"   # индекс → коммит
```

`git add` — это не «пометить файл», а **снять с него копию сейчас**: правка,
сделанная после `add`, в индекс не попадёт, пока вы не добавите файл ещё раз.

### Статус в две буквы

`git status --short` печатает по строке на файл, и первые два символа — это
состояние: **левый про индекс, правый про рабочее дерево**.

| Строка | Что значит |
|---|---|
| `?? file` | git про файл не знает (untracked). В VS Code буква **U** |
| `A  file` | файл добавлен в индекс |
| ` M file` | файл изменён, но в индекс не добавлен |
| `M  file` | изменения добавлены в индекс |
| `MM file` | часть изменений в индексе, а после этого файл правили ещё |

### Два `diff`, и это не опечатка

Раз слоёв три, то и сравнивать можно по-разному:

```bash
git diff            # рабочее дерево против индекса — «что я ещё не добавил»
git diff --cached   # индекс против последнего коммита — «что уйдёт в коммит»
git diff --stat     # то же, но сводкой: файлы и количество строк
```

**Пустой `git diff` не значит «изменений нет».** После `git add` он пустеет,
потому что рабочее дерево и индекс совпали, — а правка никуда не делась,
она переехала слоем ниже и видна через `--cached`. Это одна из самых частых
причин «я же ничего не менял».

### Что лежит внутри `.git`

Тут снимается вся магия. Три файла, которые можно прочитать `cat`-ом:

```bash
cat .git/refs/heads/main    # 40 символов — и это вся ветка (в свежем репозитории)
cat .git/HEAD               # ref: refs/heads/main
git cat-file -p HEAD        # сам коммит как обычный текст
```

Вывод последней команды:

```
tree a8f655b22f5aebd6d597dc4eef80ad92cc480092
parent be68bbada2c97bf6c1fb1e5d09a8631bd0be15e0
author Тестировщик <qa@example.com> 1789047176 +0300
committer Тестировщик <qa@example.com> 1789047176 +0300

добавил monolith
```

Отсюда три вывода, на которых держится весь остальной git:

- **Ветка — это файл с сорока символами.** Она не хранит код, не хранит копию
  проекта и не хранит «свои» коммиты — только один SHA. Поэтому сотни веток
  в `wl-e2e` не весят ничего. В большом репозитории ветки после уборки
  упакованы в один файл `.git/packed-refs` — та же пара «SHA имя», строка
  на ветку, и `cat .git/refs/heads/main` там ответит `No such file`.
  Надёжно в любом репозитории: `git rev-parse main`.
- **`HEAD` — указатель на ветку.** Буквально строка `ref: refs/heads/main`.
  Отсюда `HEAD~1` — «на один коммит назад от того, куда смотрит HEAD».
- **Коммит — это текст:** снимок файлов (`tree`), предыдущий коммит (`parent`),
  автор, сообщение. Первый коммит в репозитории — единственный без `parent`,
  и именно ссылки `parent` склеивают историю в цепочку.

## Как читать дифф

Пример: [`02-reading-a-diff.sh`](examples/02-reading-a-diff.sh)

Этой темы на занятии не было, а вопросов по ней оказалось больше, чем по любой
другой. Разбираем вывод по строкам:

```
diff --git a/suites.txt b/suites.txt     a/ — «было», b/ — «стало»
index a061010..971b11c 100644            SHA содержимого до и после, права файла
--- a/suites.txt                         какой файл слева
+++ b/suites.txt                          и какой справа
@@ -1,3 +1,4 @@                          кусок: в старом файле строки с 1-й,
                                         всего 3; в новом с 1-й, всего 4
 widgets                                 строка без знака — контекст,
 monolith                                она не менялась
 explorer
+schedule                                добавлено (в VS Code — зелёным)
```

**Контекстные строки** — не мусор: git всегда печатает по три соседние строки
вокруг правки, чтобы было видно, куда она попала. Из этого же правила растёт
поведение `git add -p` (ниже) и то, какие правки конфликтуют при слиянии
([урок 9](../lesson-09/README.md#где-проходит-граница-конфликта)).

Сводка `--stat` читается так:

```
 suites.txt | 1 +
 1 file changed, 1 insertion(+)
```

Слева файл, потом сколько строк затронуто, потом столбик из `+` и `-`.
При больших правках `+3000 −1600` — это не «3000 строк файла», а сколько
строк добавлено и удалено.

Два места, где все спотыкаются:

1. **Правка одной строки — это `-1/+1`.** У git нет «изменённой строки»:
   старая удаляется, новая добавляется. Поэтому «два изменения» в счётчике
   при одной правке — норма.
2. **`\ No newline at end of file`.** Маркер относится к строке над ним и
   означает, что файл кончался без перевода строки. Если дописанное
   «склеилось» с предыдущей строкой — причина в этом.

Когда правка сидит внутри длинной строки (а в тестах это почти всегда — селектор
внутри `getByRole(...)`), помогает:

```bash
git diff --word-diff        # подсветит слова, а не строки целиком
```

## Ветки и `detached HEAD`

Пример: [`03-branches-and-detached-head.sh`](examples/03-branches-and-detached-head.sh)

### `switch` вместо `checkout`

Старый `checkout` делал три несвязанных дела, в версии 2.23 его разделили:

| Что делаем | Сейчас | Старое (встретится везде) |
|---|---|---|
| переключиться на ветку | `git switch main` | `git checkout main` |
| создать и переключиться | `git switch -c ИМЯ` | `git checkout -b ИМЯ` |
| отбросить правку в файле | `git restore файл` | `git checkout -- файл` |

Имя ветки в проекте — по конвенции `AUT-{тикет}-C{кейс}-{описание}`.

### Переключение переписывает файлы в папке

Это не копия проекта на диске и не «другая версия папки». Файл один, и git
приводит его к состоянию той ветки, куда вы перешли. Открытая вкладка
в VS Code обновится сама.

### Грязное дерево: правило, а не лотерея

Все слышали «перед переключением закоммить или спрячь». На деле:

> **git переносит незакоммиченную правку на другую ветку, если переключение
> её не затрёт, и отказывается, если затрёт.**

Новый файл, которого на второй ветке нет вообще, переедет с вами — затирать
нечего. Правка в файле, который на ветках разный, даст:

```
error: Your local changes to the following files would be overwritten by checkout:
	suites.txt
Please commit your changes or stash them before you switch branches.
Aborting
```

Потерять правку при переключении нельзя: либо перенесёт, либо остановится.
Отсюда практическое: «в прошлый раз прокатило» ничего не доказывает.
Что делать с незаконченной правкой по-настоящему — `git stash` ниже.

### `detached HEAD`

Состояние, в которое рано или поздно попадают все: `HEAD` указывает не на ветку,
а прямо на коммит.

```bash
git switch --detach HEAD~1    # попасть сюда осознанно
git status -sb | head -1      # ## HEAD (no branch)  ← опознавательный знак
git switch -                  # выйти: «-» = предыдущая ветка, как в cd -
```

Чаще всего попадают случайно: `git checkout <sha>`, переключение на тег
и середина `git bisect`.

Ничего не сломано: файлы на месте, история цела. Единственная особенность —
**коммит, сделанный здесь, не принадлежит ни одной ветке**. Он валидный
(см. [уточнение 3](#3-коммит-в-detached-head-не-улетает-в-никуда)), но найти
его можно только через `reflog`.

## `.gitignore` и уборка

Пример: [`04-gitignore-and-clean.sh`](examples/04-gitignore-and-clean.sh)

Настоящий `.gitignore` из `wl-e2e`:

```
node_modules/
test-results/
playwright-report/
**/tests/**/*.png
**/config/.env.*.secure
**/config/.env.*.secure.*
```

Последние две строки — самые важные: **в репозиторий не должны попадать креды**.
`.env.*.secure` содержат логины и пароли тестовых бизнесов, а вторая строка
ловит любые копии рядом (`.draft`, `.bak-*`).

### Ловушка: на отслеживаемый файл ignore не действует

Классическое «добавил в `.gitignore`, а он всё равно виден». Ошибки здесь нет:

> `.gitignore` решает ровно одно — **брать ли файл под наблюдение**. Файл,
> который уже отслеживается, продолжает отслеживаться, что бы в ignore
> ни написали.

Как файл туда попадает: кто-то добавил его через `git add -f` (в том числе
Claude, который иногда доносит в коммит лишнее) либо добавил ещё до появления
правила. Лечится явно:

```bash
git rm --cached ФАЙЛ      # убрать из ИНДЕКСА, файл на диске оставить
git commit -m "перестал отслеживать ФАЙЛ"
```

`--cached` здесь про индекс, а не про какой-то кэш: без него `git rm` удалит
файл и с диска.

### `git clean` — вымести мусор после прогона

| Флаг | Что делает |
|---|---|
| `-n` | dry run: только показать, что удалилось бы |
| `-d` | заходить и в неотслеживаемые папки, не только по файлам |
| `-x` | не щадить то, что перечислено в `.gitignore` |
| `-f` | собственно удалить (без него git откажется) |

`git clean -nd` не покажет `test-results/` — она в `.gitignore`. Именно поэтому
после прогона Playwright папка никуда не девается, и нужен `-x`.

> ⚠️ Всегда сначала `-n`. `git clean -fdx` в рабочем проекте снесёт
> `node_modules/` и файлы `.env.*.secure`, которых нет в репозитории.

## Археология: кто и когда сломал тест

Пример: [`05-archeology.sh`](examples/05-archeology.sh)

Всё, что было до, — про то, как записать историю. Это — про то, как её читать,
когда тест вчера проходил, а сегодня красный.

### Когда изменилась вот эта строка

```bash
git log --oneline -S '"Book"' -- tests/     # где изменилось ЧИСЛО вхождений строки
git log --oneline -G 'Book Now' -- tests/   # регулярка по тексту дифа
```

`-S` («pickaxe») считает, сколько раз подстрока встречается в файле до и после
коммита, и оставляет только те коммиты, где это число изменилось.

**Кавычки в поиске — не педантизм.** При переименовании `"Book"` → `"Book Now"`:

| Ищем | Найдётся ли коммит переименования | Почему |
|---|---|---|
| `-S '"Book"'` | **да** | подстроки `"Book"` было одно вхождение, стало ноль |
| `-S 'Book'` | **нет** | подстроки `Book` как было одно, так и осталось |

Ищите строку вместе с её границами, иначе самое интересное переименование
пройдёт мимо.

`--` после команды означает «дальше пути, а не ветки»: снимает двусмысленность
и ограничивает поиск папкой.

**Зачем на работе:** «тест падает на `getByRole('button', { name: 'Book' })`» —
одна команда, и виден коммит, в котором селектор перестал существовать,
с автором и датой.

### Кто написал вот эту строку

```bash
git blame -- tests/C20992.spec.ts
```

Построчно: коммит, автор, дата последней правки строки. В VS Code то же самое
без команды — две встроенные настройки (`Ctrl+,` → поиск `git blame`):

- `git.blame.editorDecoration.enabled` — автор и дата серым в конце строки;
- `git.blame.statusBarItem.enabled` — то же в строке состояния.

Плюс панель **Timeline** в Explorer: вся история конкретного файла списком.
(Команды `Toggle Line Blame` и `File History` — это расширение **GitLens**,
у вас его может не быть.)

### Прочитать файл из другого коммита, не переключаясь

```bash
git show HEAD~2:tests/C20992.spec.ts
```

Синтаксис `<ссылка>:<путь>` достаёт содержимое файла из любого коммита или
ветки, рабочее дерево не трогается вообще. **Запомнить отдельно:** в уроке 9
на этой команде держится весь процесс открытия PR-ов.

### `git bisect run` — git сам находит сломавший коммит

История в двадцать коммитов, тест был зелёный, стал красный. Перебирать
вручную — двадцать прогонов. Вместо этого:

```bash
GOOD=$(git rev-parse HEAD)        # заранее запомнить заведомо рабочий коммит
git bisect start HEAD "$GOOD"     # сначала плохой, потом хороший
git bisect run ./run-test.sh      # git сам гоняет команду на каждом шаге
git bisect reset                  # ОБЯЗАТЕЛЬНО: иначе остаётесь в detached HEAD
```

`bisect` — двоичный поиск по истории: git встаёт посередине диапазона
и проверяет, каждый ответ уполовинивает остаток. Тысяча коммитов —
десять проверок. `run` читает **код возврата** команды: `0` — коммит хороший,
`1`–`127` — плохой, `125` — «этот коммит проверить нельзя», git его
пропустит; `128` и выше — bisect прервётся.

Как читать вывод — см. [уточнение 1](#1-git-bisect-называет-первый-сломанный-коммит):
ответ ровно один, и это строка `… is the first bad commit`.

В `wl-e2e`:

```bash
git bisect start HEAD HEAD~50
git bisect run bash -c 'cd projects/monolith && yarn case C20992'
```

Две оговорки. `yarn case` без env-файлов печатает `MISSING` и выходит
с кодом 1 — bisect сочтёт такой коммит плохим, хотя тест не запускался;
в своём скрипте на этот случай возвращайте `125`. И прогон идёт против
живого стенда: один флейк — и ответ неверный, поэтому найденный коммит
проверьте ещё раз руками.

## Откаты

Пример: [`06-undo.sh`](examples/06-undo.sh)

### `amend` — поправить последний коммит

```bash
git commit --amend -m "исправленное сообщение"
git commit --amend --no-edit          # доложить забытый файл, сообщение не трогая
```

После `amend` короткий SHA другой — значит это **другой коммит**. `amend`
не правит коммит, он делает новый вместо него, а старый бросает. Отсюда
правило: только для коммита, который ещё не ушёл на сервер.

### `add -p` — закоммитить только часть правок

В файле две правки: нужная и отладочный `console.log`. Коммитить надо первую.

```bash
git add -p parts.txt      # git показывает кусок за куском и спрашивает
```

Ответы: `y` взять · `n` пропустить · `s` разбить на более мелкие · `q` выйти ·
`?` список всех вариантов.

**Почему `s` иногда не предлагается.** Git склеивает правки в один кусок, если
между ними меньше семи неизменённых строк (по три строки контекста с каждой
стороны). Замеры на файле из двадцати строк:

| Правки в строках | Кусков в дифе |
|---|---:|
| 1 и 7 (5 строк между) | 1 |
| 1 и 8 (6 строк между) | 1 |
| 1 и 9 (7 строк между) | **2** |
| две соседние строки | 1, и `s` даже нет в списке ответов |

В VS Code то же самое мышью: выделить строки в дифе → правый клик →
**Stage Selected Ranges**.

**Зачем:** отладочный `console.log` в PR — шум для ревьюера (линтер `wl-e2e`
его не ловит). `add -p` — способ не тащить отладку в PR, не удаляя её из файла.

### `stash` — спрятать незаконченное

```bash
git stash push -m "черновик"   # снять правки, дерево становится чистым
git stash list                 # что лежит в стопке, верхнее — stash@{0}
git stash pop                  # вернуть верхнее и убрать из списка
git stash apply                # вернуть, но ОСТАВИТЬ в списке
git stash push -u              # захватить и новые (неотслеживаемые) файлы
```

> ⚠️ Без `-u` новые файлы останутся в папке и при переключении переедут
> на другую ветку вместе с вами — их легко закоммитить не туда. Git
> откажется переключаться, только если на той ветке есть отслеживаемый
> файл с тем же именем.

В VS Code: `Ctrl+Shift+P` → `Git: Stash`, `Git: Pop Latest Stash`,
`Git: Stash (Include Untracked)`.

### `restore` — выбросить правку совсем

```bash
git restore ФАЙЛ
```

Файл возвращается к состоянию **индекса**: то, что уже добавлено через `add`,
`restore` не трогает (для этого `git restore --staged`). Правка, которой
в индексе не было, стёрта: она нигде не сохранялась, и вернуть её нельзя
ничем — ни `reflog`, ни чем-то ещё. Одна из трёх необратимых команд урока —
вместе с `reset --hard` и `git clean -f`.
(Исключение: VS Code держит собственную локальную историю файла в Timeline.
Иногда спасает, полагаться нельзя.)

### `reset`: три режима

`reset` двигает **ветку** на другой коммит. Что при этом происходит с индексом
и рабочим деревом, задают флаги — это ровно те три дерева:

| Режим | Коммит | Индекс | Рабочее дерево | Когда |
|---|---|---|---|---|
| `--soft` | снят | **правка здесь** | не тронуто | «передумал насчёт сообщения» |
| `--mixed` (по умолчанию) | снят | очищен | **правка здесь** | «передумал, что класть в коммит» |
| `--hard` | снят | очищен | **очищено** | «выбросить всё» |

### `revert` — отменить, не переписывая историю

```bash
git revert --no-edit HEAD
```

`revert` не удаляет коммит — он делает **новый**, с обратными изменениями.
Оба остаются в истории.

> **Граница проходит по `push`, а не по коммиту.** Коммит ещё не ушёл
> на сервер — можно `reset` и `amend`. Уже ушёл — только `revert`. Общую
> историю не переписывают: у остальных она уже есть.

## Сеть безопасности

Пример: [`07-safety-net.sh`](examples/07-safety-net.sh)

```bash
git reflog                      # журнал всех перемещений HEAD
git reset --hard 'HEAD@{1}'     # вернуться туда, где HEAD был одно действие назад
```

`reflog` — журнал ваших действий в локальном репозитории: коммиты, переключения,
`reset`, `rebase`. Он показывает и то, что из `git log` уже выпало, и не
передаётся ни при `push`, ни при `clone`: он только ваш.

`HEAD@{1}` — **не** `HEAD~1`:

| Запись | Считает по |
|---|---|
| `HEAD~1` | цепочке `parent` — история проекта |
| `HEAD@{1}` | журналу — история ваших рук |

Сколько живут записи — см. [уточнение 4](#4-reflog-не-вечный).

### Чего `reflog` не вернёт

| Что потеряли | Вернётся? | Чем |
|---|---|---|
| **Коммит** (`reset --hard HEAD~1`, неудачный `rebase`, `amend`) | **да** | `git reflog` → `git reset --hard HEAD@{N}` |
| Правка в **рабочем дереве**, не добавленная в индекс | **нет, никогда** | — |
| Правка **в индексе** (`git add`, потом `reset --hard`) | **да, но грязно** | `git fsck --lost-found` → `dangling blob` |

Средняя строка и есть настоящая граница опасности:

> **`git add` — это уже сохранение.** Всё, что попало в индекс, git сохранил
> как объект, и его можно достать даже после `reset --hard`. Всё, что лежало
> только в папке, не сохранялось нигде.

Отсюда правило полезнее, чем «будьте осторожны»: **коммитьте чаще и добавляйте
в индекс раньше**. Не ради красивой истории, а ради того, что испорченный
коммит правится, а испорченный черновик нет.

## Приложение: bash и редактор

Пример: [`08-bash-and-editor.sh`](examples/08-bash-and-editor.sh)

Минимум, которым набирались все примеры:

| Команда | Что делает |
|---|---|
| `mkdir -p путь` | создать папку вместе с родителями, не ругаться, если есть |
| `echo текст > файл` | записать в файл, **перезаписав** его |
| `echo текст >> файл` | дописать в конец |
| `printf 'a\nb\n' > файл` | то же, но понимает `\n` (в отличие от `echo`) |
| `cat файл` | напечатать содержимое |
| `touch файл` | создать пустой файл |
| `cp откуда куда` · `rm -f файл` | скопировать · удалить |
| `ls -a` | показать и скрытые файлы (те, что с точки) |
| `chmod +x файл` | сделать файл исполняемым |
| `команда1 && команда2` | выполнить вторую, только если первая прошла успешно |
| `команда1 \| команда2` | пайп: вывод первой отдать на вход второй |
| `$(команда)` | подставить вывод команды в это место |
| `grep -c 'что'` | посчитать совпадения вместо того, чтобы их печатать |

> Один `&` вместо двух — совсем другая команда: «запусти первое в фоне».
> Цепочка при этом разваливается, и следующая команда выполняется
> в неожиданном состоянии.

Настройки, которые ставятся один раз на машину (`--global` пишет
в `~/.gitconfig`, без него — только в текущий репозиторий):

```bash
git config --global user.name  "Имя Фамилия"      # попадают в каждый коммит
git config --global user.email "you@wellnessliving.com"
git config --global core.editor "code --wait"     # см. уточнение 2
git config --global pull.rebase false             # git pull = fetch + merge; урок 9 на это рассчитывает
```

`code .` открывает текущую папку в VS Code, `code -r .` — в уже открытом окне.

Про редактор — в
[уточнении 2](#2-без--m-открывается-nano-а-не-vim-и-выходят-из-них-по-разному),
про `git commit -m` против `-am` — в
[уточнении 7](#7-git-commit--am-берёт-только-отслеживаемые-файлы),
и то и другое — в самом примере.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **рабочее дерево** (working tree) | файлы, которые вы видите в папке и правите редактором |
| **индекс** (staging area, index) | черновик следующего коммита; промежуточный слой между папкой и историей |
| **коммит** | снимок состояния, сохранённый навсегда: автор, дата, сообщение, ссылка на предыдущий коммит |
| **ветка** | файл с одним SHA — указатель на коммит. Не копия проекта |
| **`HEAD`** | указатель на то, где вы сейчас. Почти всегда — на ветку, а ветка на коммит |
| **`detached HEAD`** | `HEAD` указывает прямо на коммит, а не на ветку. Коммит, сделанный здесь, не принадлежит ни одной ветке |
| **`HEAD~N`** | на N коммитов назад по цепочке `parent` |
| **`HEAD@{N}`** | где `HEAD` был N ваших действий назад (по `reflog`) |
| **`reflog`** | локальный журнал перемещений `HEAD`. Не передаётся при `push`/`clone` |
| **кусок / hunk** | связный участок дифа: изменённые строки плюс по три строки контекста вокруг |
| **отслеживаемый файл** (tracked) | файл, который сейчас есть в индексе. После `git rm --cached` — снова неотслеживаемый |
| **dangling blob** | сохранённый объект, до которого не дотянуться ни из одного коммита |
