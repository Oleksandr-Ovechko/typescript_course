## 1. Настроить редактор

```bash
git config --global core.editor "code --wait"
git var GIT_EDITOR
```

Прислать вывод второй команды. Ожидается `code --wait`.

Если напечаталось что-то другое — разберитесь почему, это и есть задание.
Подсказки: имя ключа пишется без опечаток (`core.editor`, а не `core.editoer`,
и git об опечатке не сообщит); переменная окружения `GIT_EDITOR` перебивает
настройку.

## 2. Learn Git Branching

[learngitbranching.js.org](https://learngitbranching.js.org/?locale=ru_RU) —
вкладка **«Основы»** целиком. Занимает 20–30 минут, всё в браузере,
устанавливать ничего не нужно.

Это тренажёр с визуализацией графа: видно, как коммиты и ветки двигаются
от каждой команды. После него `HEAD~1`, `switch` и `reset` перестают быть
абстракцией.

## 3. Устроить `git bisect`

В своей песочнице: **десять коммитов**, в одном из них ломается проверка.

Как собрать (можно скопировать и поправить под себя):

```bash
echo 'ok' > flag.txt && git add . && git commit -m "старт"
printf '#!/usr/bin/env bash\ngrep -q ok flag.txt\n' > check.sh && chmod +x check.sh
git add . && git commit -m "скрипт проверки"
GOOD=$(git rev-parse HEAD)
for i in 1 2 3 4; do echo "правка $i" >> notes.txt; git add .; git commit -m "правка $i"; done
echo 'СЛОМАЛ' > flag.txt && git commit -am "здесь всё сломалось"
for i in 5 6 7; do echo "правка $i" >> notes.txt; git add .; git commit -m "правка $i"; done
```

Дальше найти сломавший коммит **через `git bisect run`**, не глядя в лог.

Прислать строку с ответом — ту, где написано `is the first bad commit`, —
и сказать, какое у этого коммита сообщение. Не забыть `git bisect reset`.

## 4. Потерять и вернуть коммит

```bash
echo "важное" >> notes.txt && git commit -am "ценный коммит"
git reset --hard HEAD~1        # коммита больше нет
git log --oneline | head -3    # убедиться, что его правда нет
```

Вернуть его через `reflog`. Прислать вывод `git reflog | head -5` и команду,
которой вернули.

## 5. Три вопроса без гугла

Ответить своими словами, по паре фраз:

1. Чем `git reset --soft` отличается от `--hard`?
2. Что `reflog` **не** вернёт?
3. Почему `.gitignore` не помог с файлом, который уже отслеживается?

## 6. Найти правку селектора в `wl-e2e`

Взять любой свой тест и найти, когда в нём последний раз менялся любой
селектор:

```bash
cd <ваша папка wl-e2e>
git ls-files '*C20992.spec.ts'                      # сначала убедиться, что путь есть
git log --oneline -S '"Book"' -- '*C20992.spec.ts'
```

Подставить свой кусок селектора и номер своего кейса. Прислать найденный коммит,
автора и дату (`git show --stat <sha> | head -5`).

Если ничего не нашлось — попробуйте искать строку **вместе с кавычками**
и без них, и объясните, почему результаты разные. Это половина задания.
