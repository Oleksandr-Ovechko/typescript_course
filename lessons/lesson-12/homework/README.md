## 1. Три `isVisible` с тайм-аутом

В своих хелперах (`C….helpers.ts` своих кейсов) найдите вызовы
`isVisible` с тайм-аутом:

```bash
cd ~/work/wl-e2e
git grep -n "isVisible({ *timeout" -- '**/C122691.helpers.ts'    # номер своего кейса
```

Без номера команда найдёт тысячи строк по всему проекту.

Возьмите три и для каждого решите, что автор имел в виду:

| Что имели в виду | Замена |
|---|---|
| «дождись» — элемент обязан появиться | `await expect(x).toBeVisible()` |
| «элемент необязательный — подожди, но не падай» | `await x.waitFor({ state: 'visible', timeout }).then(() => true, () => false)` |
| «есть ли он прямо сейчас» | `await x.isVisible()` без аргументов |

Подсказка, как отличить: посмотрите, что код делает дальше. Если после
`false` тест падает или бросает ошибку — это «дождись». Если идёт по другой
ветке и продолжает — «необязательный». Если проверка стоит сразу после
действия, которое точно завершилось, — возможно, «прямо сейчас».

**Готово, когда** прислано три строки `файл:строка` и для каждой —
выбранная замена и одно предложение «почему». Менять код и коммитить
не нужно.

## 2. Один `.first()`

Найдите в своём кейсе `.first()`, который выбирает из списка «первый
попавшийся», и замените его сужением областью:

```ts
// было: первая кнопка Book — какая окажется первой, зависит от порядка
await page.getByRole('button', { name: /^Book / }).first().click();
// стало: строка списка, в которой есть «Yoga», и кнопка в ней
await page.getByRole('listitem').filter({ hasText: 'Yoga' }).getByRole('button').click();
```

Это пример с занятия. В монолите контейнером обычно служит строка
таблицы, модальное окно или блок формы.

Способы сузить: `.filter({ hasText })`, цепочка от контейнера,
`exact: true`. Какой контейнер у вашего элемента — смотрите в трейсе или
в DevTools.

Проверьте, что новый локатор находит ровно один элемент, — временной
строкой перед действием:

```ts
await expect(newLocator).toHaveCount(1);
```

**Готово, когда** кейс проходит, `toHaveCount(1)` не падает, и присланы
старый и новый локатор. Временную строку потом уберите.

## 3. Pick locator против хелпера

Откройте свой кейс в UI-режиме:

```bash
cd ~/work/wl-e2e/projects/widgets        # или monolith

```

Окружение — стенд, на котором живёт ваш кейс (`staging-exp1`…`staging-exp8`).
Нужен и секретный файл `config/.env.staging-exp1.secure`: его нет в git,
его копирует с сервера генерации скрипт из корня `wl-e2e` —
`./test-server-scripts/pull-generation-envs.sh --env staging-exp1 --project widgets`.

Запустите кейс, дождитесь, пока он пройдёт, и в трейсе выберите три
шага с кликом или вводом. Для каждого нажмите **Pick locator**, наведите
на элемент и сравните предложенный локатор с тем, что стоит в хелпере.

Запишите три пары и для каждой ответьте:

- совпадают ли они;
- если нет — какой переживёт смену вёрстки (обёртку, замену `div` на
  `button`), а какой нет;
- если Pick locator предложил `getByText` — почему не `getByRole`
  (подсказка: есть ли у элемента роль).

**Готово, когда** прислана таблица «в хелпере · из Pick locator · какой
устойчивее и почему».
