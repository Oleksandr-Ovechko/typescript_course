# Урок 12. Локаторы · откуда у объекта методы

Первая половина — почему локатор «не находит»: он ищет заново при каждом
вызове, одни методы ждут, другие нет, несколько найденных элементов —
ошибка, а виджет в iframe не виден вовсе. Вторая — вводная к прототипам:
где у локатора на самом деле лежит `click`. Подробно прототипы и классы —
на уроке 13.

Документация Playwright по теме: [локаторы](https://playwright.dev/docs/locators),
[автоожидание](https://playwright.dev/docs/actionability),
[отладка](https://playwright.dev/docs/debug).

## Уточнения к занятию

Места, где на занятии прозвучала неточность. Всё проверено запуском
в песочнице и `git grep` по рабочей ветке.

**1. Ждут не только `click`, `fill`, `check`, `expect` и `textContent`.**
Ждут почти все вызовы, которые что-то делают с одним элементом: `hover()`,
`getAttribute()`, `innerText()`, `isEnabled()`, `waitFor()` и так далее.
Не ждут только вызовы для списка — `count()`, `all()`, `allTextContents()`,
`allInnerTexts()`, `evaluateAll()` — и `isVisible()`, `isHidden()`.
И `textContent()` ждёт **элемент**, а не какой-то текст:
вернёт тот текст, что в элементе есть. → [Автоожидание](#автоожидание)

**2. В `waitFor` передают одно из четырёх состояний: `attached`, `detached`,
`visible`, `hidden`.** «Enabled», «disabled», «загрузился» — таких нет,
и Playwright падает сразу: `state: expected one of (attached|detached|visible|hidden)`.
Дождаться доступности кнопки — `expect(x).toBeEnabled()`.

**3. `expect(...)` ждёт по `expect.timeout`, а не по `actionTimeout`.**
«3 или 5 секунд, чтобы дождаться элемента» — это `expect.timeout`: 5 с,
умолчание Playwright (в конфиге `widgets` оно записано явно).
`actionTimeout` (15 с) — у действий: `click`, `fill`, `waitFor`.
→ [таблица тайм-аутов](#какой-тайм-аут-за-что-отвечает)

**4. `navigationTimeout` не относится к клику.** Он действует на `goto`,
`reload`, `goBack`, `goForward`, `waitForURL`. Клик по ссылке не ждёт,
пока загрузится новая страница, — это делает следующий шаг: `waitForURL`
или `expect` на элемент новой страницы.

**5. `toHaveText` не строгий, когда ему передают массив ожидаемых
текстов**, а не локаторов: `toHaveText(['Book Yoga', 'Book Pilates', 'Book Boxing'])`
проверяет список по порядку. С одной строкой он строгий.

**6. `getBy…` не превращаются в CSS.** `getByRole('button', { name: 'Book Yoga' })`
Playwright переводит во внутренний селектор `internal:role=button[name="Book Yoga"i]`.
CSS не умеет искать ни по тексту, ни по доступному имени — только по
тегам, классам и атрибутам. `page.locator(...)` понимает и CSS, и
собственные селекторы Playwright.

**7. Строгий режим у локаторов выключить нельзя, а для старых `page.click`
его можно включить**: `use: { contextOptions: { strictSelectors: true } }`.
В `wl-e2e` этой опции нет. → [Строгий режим](#строгий-режим)

**8. Если локатор нашёл 0 и дело в имени — сужать нечего.** `exact` и
`.filter()` только сужают поиск и из нуля ничего не сделают. Нужно
наоборот: убрать `exact`, если он стоит, и посмотреть настоящее доступное
имя в Pick locator. Сужение — для случая «нашёл несколько».
→ [Если локатор не сработал](#если-локатор-не-сработал)

**9. Объект-обёртка строки и `String.prototype` — разные объекты.** Движок
создаёт на время вызова отдельный объект `String`, а `String.prototype` —
его прототип: `Object('x') === String.prototype` — `false`.

**10. `Date` — функция, а `Date.prototype` — её свойство.** `typeof Date` —
`'function'`. Методы `getTime`, `toISOString` лежат в `Date.prototype`,
отдельном объекте. `new Date()` ставит новому объекту прототипом именно его.

**11. `instanceof` смотрит всю цепочку, а прямое сравнение прототипа —
только первое звено.** `[] instanceof Object` — `true`, а
`Object.getPrototypeOf([]) === Object.prototype` — `false`: первым в
цепочке массива стоит `Array.prototype`.

**Мелочи.**

- `isVisible(` в `wl-e2e` на момент занятия — около **8 300** вызовов, из них
  около **3 500** — с тайм-аутом. К 22.10 с тайм-аутом осталось около 2 700
  на `test-generation` и около 1 000 на `draft`.
- `getByTestId` в проекте есть — один вызов.
- Правило про `.first()` — **A8** в `RULES.md`.
- Не все тесты виджетов работают через iframe: часть открывает виджет прямо
  по его адресу, без страницы-хозяина (например, `C156177`), — там
  `frameLocator` не нужен.
- `following-sibling::tr[…][1]` в XPath — следующая **соседняя** строка
  таблицы, а не предок или потомок.
- В `--debug` между шагами проходят секунды, а не миллисекунды: этого
  с запасом хватает, чтобы список загрузился за свои 300 мс.
- `isVisible({ timeout })` обычно не роняет тест. Он возвращает `false`,
  и код молча идёт по ветке «элемента нет». В этом и опасность.
- `console.log(Object.prototype)` в Node печатает `[Object: null prototype] {}`:
  методы прототипов неперечисляемые. Список —
  `Object.getOwnPropertyNames(Object.prototype)`; в DevTools браузера
  объект раскрывается кликом.
- Записать свойство в строку нельзя с ошибкой только в строгом режиме
  (файлы-модули всегда строгие). В обычном скрипте присваивание молча
  пропадает.

## Режимы с окном

По умолчанию тесты идут **без окна** (headless). Посмотреть на тест
своими глазами можно четырьмя способами:

| Режим | Что это | Когда |
|---|---|---|
| `--headed` | обычный прогон, но браузер видно. Ничего не замедляет и никого не ждёт | посмотреть, что делает тест |
| `--ui` | окно со списком тестов, запуск по клику, трейс шаг за шагом, **Pick locator** | разбирать и чинить один тест |
| `--debug` | инспектор: тест стоит перед каждым действием, шаг — кнопкой. Сам включает окно, один воркер и снимает тайм-аут | понять, на каком шаге что происходит |
| `codegen` | браузер плюс окно с кодом: кликаете — пишется `getByRole(...)`, кнопками добавляются проверки (виден, текст, значение поля) | черновик локатора |

`codegen` пишет черновик, а не готовый хелпер: правил проекта (A8, S3)
он не знает. У нас тесты пишет Клод, но `codegen` полезен, чтобы быстро
увидеть, какой локатор Playwright выбрал бы сам.

**`page.pause()`** — точка останова прямо в коде. В обычном прогоне она
**пропускается**: срабатывает только с `--headed` или `--debug`.

**В Docker режимы с окном не работают**: в контейнере нет экрана. Поэтому
на CI и в регрессии `page.pause()` пропускается, а `--ui`, `--headed`
и `--debug` — только на своей машине.

UI-режим меняет оболочку и включает трейс, но **правила ожидания те же**.
Тест, который падает в UI-режиме и проходит без него, падает от
замедления, а не от другого способа ждать.

Пример — [`01-modes-and-pause.sh`](examples/01-modes-and-pause.sh).

## Локатор: описание, а не элемент

```ts
const bookButtons = page.getByRole('button', { name: /^Book / });
console.log('до goto:', await bookButtons.count());              // 0
await page.goto('/');
console.log('сразу после goto:', await bookButtons.count());     // 0
await expect(bookButtons).toHaveCount(3);
console.log('после expect:', await bookButtons.count());         // 3
```

Одна переменная — три разных ответа. **Локатор — описание того, как найти
элемент** («кнопка, имя которой начинается с Book»), а не сам элемент.
Искать он начинает только тогда, когда с ним что-то делают, и ищет **заново
каждый раз**. Та же ленивость, что у генератора в уроке 10.

Поэтому локатор можно создать до `goto` — он ничего не ищет, пока не
попросили. И поэтому ответ зависит от момента: до `goto` страницы нет,
сразу после `goto` список ещё грузится с API, после `expect` кнопки уже есть.

**В `--debug` «сразу после goto» показывает 3.** Не потому что режим
особенный, а потому что между шагами проходят секунды, пока вы жмёте
кнопку, и список успевает загрузиться. Пример замедляет браузер на
полсекунды (`slowMo`) и получает то же 3 без всякого `--debug`.

Отсюда вывод, который на занятии сделали сами: **«в `--debug` работает»
ничего не доказывает.** Отладка медленнее обычного прогона и прячет гонку.

Пример — [`02-lazy-and-autowait.sh`](examples/02-lazy-and-autowait.sh).

## Автоожидание

`count()` сразу после `goto` не дождался кнопок, а `expect(...).toHaveCount(3)`
дождался. **Автоожидание** — Playwright сам повторяет проверку, пока
условие не выполнится или не кончится тайм-аут.

Изнутри это видно в логе действия в трейсе (урок 11): `waiting for
getByRole(...)` → `locator resolved to 0 elements` → `resolved to 3` →
`element is visible, enabled and stable` → клик.

| Ждут | Не ждут — отвечают «про сейчас» |
|---|---|
| действия: `click`, `fill`, `check`, `hover`… | `count()`, `all()` |
| проверки `expect(...)` | `allTextContents()`, `allInnerTexts()`, `evaluateAll()` |
| чтение одного элемента: `textContent()`, `getAttribute()`, `innerText()`, `isEnabled()`, `waitFor()` | `isVisible()`, `isHidden()` |

Запоминать проще через исключения: **не ждут только эти семь** — вызовы
для списка и `isVisible`/`isHidden`, всё остальное у локатора ждёт, пока
элемент появится.

**`waitFor`** ждёт одно из четырёх состояний: `attached` (есть в DOM),
`detached` (исчез из DOM), `visible` (виден — по умолчанию), `hidden`
(скрыт или его нет). Для доступности кнопки — `expect(x).toBeEnabled()`,
для загрузки страницы — `page.waitForLoadState()`.

### Какой тайм-аут за что отвечает

Вопрос с занятия. Значения — из `projects/monolith` и `projects/widgets`
`playwright.config.ts`:

| Что ждёт | Ключ конфига | У нас |
|---|---|---|
| весь тест целиком | `timeout` | 60 с |
| `expect(...).toBeVisible()`, `toHaveText()` и другие проверки | `expect.timeout` | 5 с — умолчание Playwright |
| `click`, `fill`, `check`, `hover`, `textContent()`, `waitFor()` — действия с элементом | `use.actionTimeout` | 15 с |
| `goto`, `reload`, `goBack`, `goForward`, `waitForURL` | `use.navigationTimeout` | 15 с |

На медленных стендах числа больше: конфиг умножает их на `WL_TIMEOUT_SCALE`
из `config/.env.<окружение>` — у `wl-aut-*` он равен 2.

Явный `{ timeout }` в самом вызове всегда сильнее конфига. Клика в строке
навигации нет: кликнули по клиенту — и дальше ждёт следующий шаг,
`waitForURL` или `expect` на элемент профиля.

Пример — [`02-lazy-and-autowait.sh`](examples/02-lazy-and-autowait.sh).

## `isVisible()` не ждёт

В `wl-e2e` `isVisible(` вызывается тысячи раз, и заметная часть — с
тайм-аутом (на 22.10: на `test-generation` около 9 400 вызовов, из них
около 2 700 с тайм-аутом; на `draft` — около 4 200 и 1 000):
`isVisible({ timeout: 5_000 })`, «подожди до пяти секунд».
Но этот тайм-аут **игнорируется** — в типах Playwright он помечен
`@deprecated This option is ignored`. Баннер, который появляется через
секунду, `isVisible` с тайм-аутом в пять секунд не видит: отвечает `false`
мгновенно.

Это правило **W10** в `wl-e2e/RULES.md`. Запрещён не сам `isVisible()`,
а вызов с тайм-аутом, который читается как «подожди», а означает
«прямо сейчас».

Ошибка **тихая**: ничего не падает. `isVisible` возвращает правдоподобный
`false`, и код молча идёт по ветке «элемента нет». Если тест и упадёт,
то позже и в другом месте. Настоящий случай описан в комментарии
в `helpers/monolith/client-profile/buy-page.ts`: проверка `isVisible()`
сразу после `networkidle` застала страницу оплаты недорисованной,
пропустила ветку договора, и тест упал дальше — на кнопке Cash, которой
тоже ещё не было.

| Задача | Как писать |
|---|---|
| дождаться, что элемент появился | `await expect(x).toBeVisible()` |
| элемент необязательный — подождать, но не падать | `await x.waitFor({ state: 'visible', timeout }).then(() => true, () => false)` |
| осознанно спросить «есть ли сейчас» | `await x.isVisible()` — **без аргументов** |

Это самый вероятный ответ на «`getByRole` иногда не успевал»: не локатор
не успевал, а проверка перед ним не ждала.

Пример — [`03-is-visible.sh`](examples/03-is-visible.sh).

## Строгий режим

```ts
await page.getByRole('button', { name: 'Book' }).click();
```

На странице три кнопки: «Book Yoga», «Book Pilates», «Book Boxing».
Клик не попадёт ни в одну — тест падает:

```text
Error: locator.click: Error: strict mode violation: getByRole('button', { name: 'Book' }) resolved to 3 elements:
    1) <button>Book Yoga</button> aka getByRole('button', { name: 'Book Yoga' })
    2) <button>Book Pilates</button> aka getByRole('button', { name: 'Book Pilates' })
    3) <button>Book Boxing</button> aka getByRole('button', { name: 'Book Boxing' })
```

**Строгий режим** — если локатор нашёл больше одного элемента там, где
нужен ровно один, вызов падает. Playwright не угадывает, какой вы имели
в виду. Три вещи из этой ошибки:

1. `name: 'Book'` подошёл всем трём — имя ищется как **подстрока**.
2. Упало **сразу**, не дожидаясь тайм-аута: ответ уже неоднозначный.
3. Строки `aka …` — готовые точные локаторы.

У локатора строгий режим — не настройка, выключить его нельзя. Действует
он везде, где вызов имеет смысл только для одного элемента:

| Строгие — падают на нескольких | Не строгие |
|---|---|
| действия: `click`, `fill`, `check`… | `count()`, `all()`, `allTextContents()` |
| `textContent()`, `isVisible()`, `getAttribute()` | `.first()`, `.nth()`, `.last()` — сами выбирают один |
| проверки одного элемента: `toBeVisible`, `toHaveText('…')` | проверки списка: `toHaveCount`, `toHaveText([...])` — массив текстов |
| | **старые методы `page.click('селектор')`, `page.fill(...)`** |

**Последняя строка — ловушка.** Старый `page.click(селектор)` не строгий
и молча кликает первый найденный элемент. В `wl-e2e` таких вызовов
немного — около десятка, но часть — в общих
хелперах (`clients-report.ts`, `general-report.ts`,
`class-schedule-setup-page.ts`). Ошибка в общем хелпере задевает все
тесты, которые его зовут. Включить строгость для старых методов можно
опцией `strictSelectors: true` в `contextOptions`, но в `wl-e2e` её нет.

Пример — [`04-strict-mode.sh`](examples/04-strict-mode.sh).

## Какой локатор выбрать

Все `getBy…` — удобные способы найти элемент. Тот же элемент можно
найти и CSS-селектором в `page.locator(...)`, но CSS видит только
вёрстку: теги, классы, атрибуты. Разница — в том, **что сломается
первым**. CSS ломается, когда добавили обёртку или заменили `div` на
`button`. Роль и подпись привязаны к тому, что видит пользователь.

| Порядок | Метод | Когда |
|---:|---|---|
| 1 | `getByRole('button', { name })` | всё, у чего есть роль: кнопки, ссылки, поля, чекбоксы |
| 2 | `getByLabel`, `getByPlaceholder` | поля ввода |
| 3 | `getByText` | текст без роли |
| 4 | `getByTestId` | если в вёрстке есть `data-testid` |
| 5 | `page.locator('css')` | когда ничего выше не подходит |

Правило **S3** в `wl-e2e/RULES.md` говорит то же короче: `getByRole`,
`getByLabel` и data-атрибуты — вместо CSS; XPath и `:nth-child` не
пропускает гейт. Места для `getByText` и `getByPlaceholder` S3 не задаёт —
порядок в таблице подсказывает, что пробовать раньше. Клод это правило
читает — оно в тех файлах, с которых он начинает работу. На деле в
проекте `.locator(` встречается в несколько раз чаще, чем `getByRole(`
(на `test-generation` 22.10 — около 144 000 против 22 000).

`getByTestId` у нас почти не используется: разработчики монолита
и виджетов не ставят `data-testid`. Вопрос о том, чтобы начали ставить,
поднят. Если появятся — `getByTestId` станет самым надёжным вариантом.

### Как совпадает имя

**Доступное имя** (accessible name) — то, как элемент называет себя для
экранного диктора: текст кнопки, подпись поля, `aria-label`. Именно его
ищет `name` в `getByRole`.

| Локатор | Найдено | Почему |
|---|:---:|---|
| `getByRole('button', { name: 'book yoga' })` | 1 | подстрока, без учёта регистра |
| `getByRole('button', { name: 'Yoga' })` | 1 | подстрока |
| `getByRole('button', { name: 'book yoga', exact: true })` | 0 | `exact` — целиком и с регистром |
| `getByRole('button', { name: 'Book Yoga', exact: true })` | 1 | |
| `getByRole('button', { name: 'Cancel' })` | 0 | «Cancel» — `div` с обработчиком клика, роли `button` у него нет |
| `getByText('Cancel')` | 1 | |
| `getByLabel('Email')` | 1 | по `<label for="email">` |
| `getByPlaceholder('Search')` | 1 | по подсказке внутри поля, подстрокой |

Роль и имя элемента видно в DevTools, во вкладке Accessibility, и в
**Pick locator** (UI-режим, трейс): навести на элемент — Playwright покажет
локатор, который выбрал бы сам. Для `div` «Cancel» он предложит `getByText`.

### Как `.first()` глушит строгий режим

Самый частый способ избавиться от «resolved to 3 elements» — дописать
`.first()`. Он выключает строгий режим, а вместе с ним и защиту:

```ts
await page.getByRole('button', { name: /^Book / }).first().click();
```

Пока список идёт «Yoga, Pilates, Boxing», это клик по Yoga. Бэкенд поменял
сортировку — и тот же код **молча** кликнул Boxing. Упал тест только на
проверке диалога; без неё прошёл бы и записал клиента не туда.

В монолите `.first()` ещё опаснее: многие элементы свёрстаны дважды —
для десктопа и скрытая копия для мобильной версии. `.first()` может взять
скрытую копию.

Правило **A8**: не действовать на `.first()` вслепую. Вместо номера —
**сузить областью**:

```ts
await page.getByRole('listitem').filter({ hasText: 'Yoga' }).getByRole('button').click();
```

Сначала строка списка, в которой есть «Yoga», и уже в ней — кнопка.
Порядок больше не важен. Другие способы сузить: `exact: true`, цепочка
от контейнера.

### XPath и `:nth-child`

Тот же выбор по номеру, только внутри селектора. Оба запрещены S3:

```text
itemRow.locator('xpath=following-sibling::tr[contains(@class,"js-content-row")][1]')
```

«Следующая соседняя строка таблицы с таким классом, первая» — сломается,
как только между строками появится ещё одна.

Пример — [`05-choosing-a-locator.sh`](examples/05-choosing-a-locator.sh).

## Виджет в iframe

Бывает наоборот: локатор точный, элемент на экране виден — а найдено ноль.
Самая частая причина — элемент внутри **iframe**, отдельной страницы внутри
страницы. Локаторы `page` туда не заглядывают:

```ts
await page.getByRole('button', { name: 'Book in widget' }).count();   // 0
const widget = page.frameLocator('iframe[name^="wl-schedule-widget:"]');
await widget.getByRole('button', { name: 'Book in widget' }).click();  // находит
```

У нас в iframe — виджеты на сайте клиента (`UI-PATTERNS.md` §15)
и **всплывающие уведомления монолита**: `page.frameLocator('#mp-note-frame')`
в `helpers/monolith/assertions.ts`.

Пример — [`06-iframe.sh`](examples/06-iframe.sh).

## Если локатор не сработал

Всё вместе — схема, которую рисовали на занятии:

```text
                         ЛОКАТОР НЕ СРАБОТАЛ
                                  │
          ┌───────────────────────┼────────────────────────┐
          ▼                       ▼                        ▼
   НАШЁЛ 0 ЭЛЕМЕНТОВ      НАШЁЛ НЕСКОЛЬКО         «НЕ УСПЕЛ»
                          (strict mode violation)
          │                       │                        │
   ┌──────┴──────┐         сузить областью:        что стоит перед ним?
   │ элемент в   │ да      • .filter({ hasText })          │
   │ iframe?     ├──►      • строка → кнопка        ┌──────┴───────┐
   └──────┬──────┘ frame-  • exact: true            │ isVisible(),  │ да
          │ нет    Locator                          │ count()?      ├──►
   ┌──────┴──────┐         НЕ .first()              └──────┬───────┘  expect(...)
   │ у элемента  │ нет     (A8)                            │ нет      .toBeVisible()
   │ есть роль?  ├──► getByText / getByLabel               ▼
   └──────┬──────┘                                 действие ждёт само —
          │ да                                     смотреть Log в трейсе:
   ┌──────┴──────┐                                 чего ждал и сколько
   │ имя совпало?│ нет  убрать exact: true, если стоит;
   │             ├──►   настоящее имя — из Pick locator
   └─────────────┘      (сужать тут нечего: найдено 0)
```

Где взять правильный локатор: **Pick locator** в UI-режиме и в трейсе,
**`codegen`**, строки **`aka`** в ошибке строгого режима.

Если действие ждёт само, а элемента всё нет — дело уже не в локаторе.
Лог шага в трейсе покажет, чего ждали; дальше — почему элемент не появился:
не выполнено условие показа, медленный ответ сервера, ошибка в консоли.

## Откуда у объекта методы

### Где у локатора `click`

Весь урок у локатора вызывали методы — `click`, `count`, `isVisible`,
`first`. Локатор — обычный объект. Где в нём лежит `click`?

```ts
const yoga = page.getByRole('button', { name: 'Book Yoga' });
typeof yoga.click;                               // 'function'
Object.hasOwn(yoga, 'click');                    // false
Object.hasOwn(Object.getPrototypeOf(yoga), 'click');   // true
```

`click` вызывается, но в самом объекте его **нет**. Он лежит в другом
объекте — **прототипе** локатора. Прототип один на все локаторы: сколько
бы их ни создали, `click` написан один раз.

**Собственное свойство** (own property) — то, что лежит в самом объекте.
`Object.hasOwn(obj, 'имя')` отвечает, собственное ли оно.

Пример — [`07-locator-prototype.sh`](examples/07-locator-prototype.sh).

### Прототип и цепочка прототипов

**Прототип** (prototype) — объект, в котором JavaScript ищет свойство,
если его нет в самом объекте. `Object.getPrototypeOf(obj)` показывает, какой.

Так устроены все значения, даже строка. Строка — примитив, не объект,
но `toUpperCase` у неё есть: он лежит в `String.prototype`. В момент
вызова движок на мгновение заворачивает строку в объект-обёртку,
находит метод в её прототипе, вызывает и выбрасывает обёртку. Поэтому
записать в строку своё поле нельзя: обёртки к тому моменту уже нет.

У прототипа тоже есть прототип:

```text
['widgets', 'monolith']  →  Array.prototype  →  Object.prototype  →  null
```

**Цепочка прототипов** (prototype chain) — объект → его прототип →
прототип прототипа → … → `null`. Свойство ищется по цепочке снизу вверх,
**первое найденное побеждает**. `suites.map`: в самом массиве нет,
в `Array.prototype` есть — найдено. Там же лежит и `Symbol.iterator`
(вопрос урока 10): поэтому `for...of` работает с любым массивом.

Это тот же механизм, что лексическое окружение в уроке 6: там переменная
искалась изнутри наружу по цепочке окружений, здесь свойство — от объекта
вверх по цепочке прототипов.

`in` смотрит всю цепочку, `Object.hasOwn` — только сам объект:
`'map' in suites` — `true`, `Object.hasOwn(suites, 'map')` — `false`.

### Своё свойство закрывает прототип

```ts
const client = { name: 'Anna' };
const namedClient = { name: 'Anna', toString() { return this.name; } };
`${client}`;        // '[object Object]'
`${namedClient}`;   // 'Anna'
```

У `client` своего `toString` нет — нашёлся `Object.prototype.toString`.
У `namedClient` свой есть — поиск на нём остановился. Затенение из урока 6,
только для свойств. Отсюда ловушка в именах тестов: `` `book for ${client}` ``
даст «book for [object Object]».

### `new` и `instanceof`

Для массивов и строк прототип ставит сам язык. Для остальных — `new`.
`Date` — это **функция**, а `Date.prototype` — её свойство, отдельный
объект с `getTime`, `toISOString` и остальным. `new Date()` создаёт
объект и ставит ему прототипом `Date.prototype`.

`x instanceof Date` — есть ли `Date.prototype` **где-то в цепочке** `x`.
Поэтому дата — ещё и `instanceof Object`, хотя её прототип —
`Date.prototype`, а не `Object.prototype`.

`class` — запись, которая создаёт такой прототип и функцию для `new`.
В `wl-e2e` классов почти нет; главный — TestRail-репортер: Playwright
делает `new TestRailReporter()` и вызывает его методы, а методы лежат
в прототипе — как `click` у локатора. Как устроены `class`, `constructor`,
`extends` — урок 13.

Пример — [`08-prototypes.ts`](examples/08-prototypes.ts).

## Итог занятия

1. `--headed` — видеть, `--ui` — разбирать, `--debug` — по шагам,
   `codegen` — черновик локатора. `page.pause()` без окна пропускается.
   В Docker режимы с окном не работают.
2. Локатор — описание, ищет заново при каждом вызове. `--debug` медленнее
   обычного прогона и прячет гонку.
3. Почти всё у локатора ждёт. Не ждут только вызовы для списка (`count()`,
   `all()`, `allTextContents()`, `allInnerTexts()`, `evaluateAll()`)
   и `isVisible()`, `isHidden()`. `expect` ждёт по
   `expect.timeout` (5 с), действия — по `actionTimeout` (15 с).
4. Тайм-аут у `isVisible` игнорируется (W10) — ждать через
   `expect(...).toBeVisible()`.
5. Нашёл несколько — строгий режим, падение сразу, подсказки `aka`.
   Старый `page.click(селектор)` не строгий.
6. Роль → подпись → текст → CSS (S3). `name` — подстрока без регистра.
   `.first()` — клик по номеру (A8). Iframe — `frameLocator`.
7. Методы лежат не в объекте, а в прототипе; поиск идёт по цепочке
   до `null`, первое найденное побеждает.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **локатор** (locator) | описание того, как найти элемент: «кнопка с именем Book Yoga». Не сам элемент — поиск идёт заново каждый раз, когда с локатором что-то делают |
| **автоожидание** (auto-waiting) | Playwright сам повторяет проверку, пока условие не выполнится или не кончится тайм-аут. `expect(...)` ждёт по `expect.timeout`, действия — по `actionTimeout` |
| **строгий режим** (strict mode) | если локатор нашёл больше одного элемента там, где нужен ровно один, вызов падает сразу |
| **доступное имя** (accessible name) | как элемент называет себя для экранного диктора: текст кнопки, подпись поля, `aria-label`. Его ищет `name` в `getByRole` |
| **прототип** (prototype) | объект, в котором JavaScript ищет свойство, если его нет в самом объекте. `Object.getPrototypeOf(obj)` |
| **цепочка прототипов** (prototype chain) | объект → его прототип → прототип прототипа → … → `null`. Свойство ищется по цепочке, первое найденное побеждает |
| **собственное свойство** (own property) | то, что лежит в самом объекте, а не в прототипе. `Object.hasOwn(obj, 'имя')` |
