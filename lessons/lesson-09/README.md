## Уточнения к занятию

Шесть мест, где на занятии прозвучала неточность. Всё проверено запуском,
документацией git и `gh api`.

### 1. В Merge Editor слева ваш вариант, а не чужой

Панели называются так же, как маркеры в файле и кнопки над ними:

| Где | Ваш вариант | Чужой |
|---|---|---|
| в файле | верхний блок, `<<<<<<< HEAD` | нижний, до `>>>>>>> <sha>` |
| кнопки над блоком | `Accept Current` | `Accept Incoming` |
| Merge Editor | **левая** панель, Current | **правая**, Incoming |

Снизу в Merge Editor — Result, то, что получится, и кнопка `Complete Merge`.
Если засомневались, где чей вариант, ориентир один и тот же во всех трёх
местах: **Current — это `HEAD`, то есть вы**.

Ошибиться здесь дорого: в отличие от синтаксической ошибки, «принял не тот
вариант» компилируется и проходит ревью.

### 2. `ort` — это не «ортогональная стратегия»

Строчка `Merge made by the 'ort' strategy` говорит про алгоритм слияния.
`ort` — акроним **«Ostensibly Recursive's Twin»** (`man git-merge`): стратегия
по умолчанию с git 2.34, написанная взамен старой `recursive`.

Она не объясняет, почему слияние прошло гладко. Гладко оно проходит, когда
правки не соприкасаются — см. [«Где проходит граница конфликта»](#где-проходит-граница-конфликта).

### 3. `push --force` запрещён правилом, а не техникой

Проверено: защиты ветки `draft` на GitHub нет (`gh api …/branches/draft/protection`
→ 404), в локальном конфиге запретов нет, хука `pre-push` в репозитории нет.

Запрет живёт в `.claude/commands/bugfix-batch.md`, правило 8. То есть
**git вас не остановит** — остановиться нужно самому. Если очень нужно
на своей ветке, то `--force-with-lease`: он хотя бы откажется, если
на сервере появилось что-то, чего вы не видели.

### 4. `merge` не переносит чужие коммиты «сверху»

Он берёт две истории и делает **один** коммит слияния с двумя родителями.
Чужие коммиты остаются на своих местах, со своими SHA и своими родителями.

«Класть коммиты сверху» — это как раз `rebase` и `cherry-pick`, то есть ровно
то, чему `merge` противопоставляется. Разбор с графами —
[`06-merge-vs-rebase.sh`](examples/06-merge-vs-rebase.sh).

### 5. Граница `revert` проходит по `push`, а не по коммиту

Пока коммит не ушёл на сервер, его можно править `amend` и снимать `reset` —
это ваша личная история. После `push` она уже у других, и остаётся только
`revert`, который отменяет коммит новым коммитом.

### 6. Worktree — не «полная копия репозитория»

Это **вторая рабочая папка одного репозитория**. `.git` внутри неё — не папка,
а файл в одну строку:

```
gitdir: /home/alex/work/wl-e2e/.git/worktrees/AUT-1566
```

История общая, объекты общие, копируются только выложенные файлы. И, что важнее
на практике, копируется **только то, что лежит в репозитории**: всё из
`.gitignore` в новую папку не попадает — ни `node_modules`, ни `.env.*.secure`.

## Свой «сервер» за одну команду

Пример: [`01-own-server.sh`](examples/01-own-server.sh)

Чтобы разобрать `push` и `pull`, GitHub не нужен. Достаточно репозитория
без рабочей папки:

```bash
git init --bare -b main ../server.git
git remote add origin ../server.git
git remote -v
git push -u origin main
git branch -vv
```

`--bare` — репозиторий **без рабочего дерева**: только история, файлов рядом
нет. Если заглянуть внутрь `server.git`, там лежит содержимое обычного `.git`
и больше ничего. Так устроен любой сервер, включая GitHub: там нет папки
с файлами, которую кто-то редактирует.

`origin` — просто **имя** для адреса. Не команда и не ключевое слово: так
по традиции называют основной удалённый репозиторий, можно было назвать
`server`. В `git remote -v` адрес печатается дважды, потому что `fetch`
и `push` можно развести на разные адреса.

`git branch -vv` показывает привязку в квадратных скобках — два `v` нужны
именно ради неё, с одним git привязку не покажет.

### Что на самом деле делает `-u`

```
git push origin ВЕТКА     пройдёт и БЕЗ -u — ветка на сервере создастся
git push                  без привязки упадёт:
                          fatal: The current branch X has no upstream branch
```

То есть `-u` (полное имя `--set-upstream`) нужен не для того, чтобы push
случился, а для того, чтобы дальше хватало голого `git push`. Ставится один
раз при первом push новой ветки.

### Где физически лежит `origin/main`

Самое частое непонимание во всём git, и снимается оно двумя командами:

```bash
cat .git/refs/heads/main            # куда смотрит НАША ветка
cat .git/refs/remotes/origin/main   # наша ЗАПИСЬ о сервере
```

Оба — файлы **у вас на диске**.

> `origin/main` не находится на сервере и не спрашивает сервер. Это ваша запись
> о том, где ветка сервера была **в момент последнего `fetch`**. Она устаревает
> молча.

Коллега может запушить пять раз — ваш `origin/main` будет показывать прошлое,
пока вы не сделаете `fetch`.

### Заодно: от чьего имени уходит коммит

Коммит подписывается тем `user.name`/`user.email`, который действует **в папке,
где выполняется команда**. С терминалом это очевидно, а вот с кнопкой в VS Code
— нет: редактор коммитит от конфига **открытой в нём папки**, а не той, где
стоит ваш терминал. Классический способ получить коммит «за коллегу»
от собственного имени — открыть в VS Code одну папку, а работать в другой.

## Отклонённый push и `fetch` против `pull`

Пример: [`02-rejected-push-and-fetch.sh`](examples/02-rejected-push-and-fetch.sh)

Коллега запушил свою правку раньше вас. Вы пробуете запушить свою:

```
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../server.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

Git отказался. **Не потому, что конфликт** — до содержимого файла он даже
не дошёл. Причина другая: на сервере есть коммит, которого нет у вас, и принять
push означало бы затереть чужую работу.

> **Отклонённый push ≠ конфликт. Отклонённый push = «ты отстал».**
> Конфликт может быть следующим шагом, а может и не быть.

`(fetch first)` — это инструкция: сначала забери.

### `fetch` забирает чужое и не трогает ваши файлы

```bash
git fetch origin
git status -sb | head -1     # ## main...origin/main [ahead 1, behind 1]
```

После `fetch` файл в папке не изменился — и это суть команды: она забрала
чужие коммиты в репозиторий, но рабочее дерево не трогала. Изменилась запись
о сервере: `origin/main` подтянулся, `main` остался на месте.

`ahead 1, behind 1` читается так: у вас есть один коммит, которого нет
на сервере, и на сервере есть один, которого нет у вас. Именно это git
и называл «fetch first».

| Команда | Что делает | Может ли упасть |
|---|---|---|
| `git fetch` | только скачивает | нет, безопасен всегда |
| `git pull` | `fetch` + `merge` | да — на второй половине |

**Практический совет:** привыкать к `git fetch` → посмотреть `git status -sb` →
`git merge`, вместо `git pull` вслепую. Одна строка статуса за секунду говорит,
чего ждать.

Посмотреть картинку целиком:

```bash
git log --oneline --graph --all --decorate
```

`--graph` рисует линии, `--all` показывает все ветки (включая `origin/*`),
`--decorate` подписывает, какие имена на каких коммитах.

### Команда, которой затирают чужую работу

```bash
git push --force              # чужие коммиты просто исчезают
git push --force-with-lease   # мягче: откажется, если на сервере есть новое
```

Про запрет — [уточнение 3](#3-push---force-запрещён-правилом-а-не-техникой).

## Конфликт

Пример: [`03-conflict.sh`](examples/03-conflict.sh)

### Где проходит граница конфликта

Конфликт возникает **не от того, что двое трогали один файл**. Он возникает,
когда двое изменили одно и то же место, и git не может решить, чей вариант
верный.

Но «мы правили разные строки» — тоже не гарантия. Замер на файле из десяти
строк: один правит строку 5, другой —

| строку | результат |
|---|---|
| 6 (соседнюю) | **конфликт** |
| 7 | слилось молча |
| 8 | слилось молча |

Правило точнее: **git сливает молча, если изменённые куски не соприкасаются** —
между ними осталась хотя бы одна нетронутая строка. Это те же куски (hunks)
и тот же контекст в три строки, что в `git add -p`
([урок 8](../lesson-08/README.md#add--p-закоммитить-только-часть-правок)).

### Маркеры

```
widgets
monolith
<<<<<<< HEAD
appointments
=======
schedule
>>>>>>> 7a4c608cb92041766f638f7b8f799e866b9aaea4
```

- `<<<<<<< HEAD` — отсюда начинается **ваш** вариант, тот, что уже был у вас;
- `=======` — разделитель;
- `>>>>>>> 7a4c608` — здесь кончается **чужой**, и указан его коммит.

Полезные команды в этот момент:

```bash
git status --short                          # UU файл — «изменён с обеих сторон»
git diff --name-only --diff-filter=U        # машинный список конфликтных файлов
```

Разрешить конфликт — это привести файл к нужному виду и убрать все три маркера.
Команды «разреши за меня» не существует.

### Пока слияние не закончено

Внутри `.git` появляются служебные файлы: `MERGE_HEAD` (с каким коммитом
сливаемся), `MERGE_MSG` (заготовка сообщения), `AUTO_MERGE`, `MERGE_MODE`.
Пока они есть, git считает, что операция идёт, и не даст переключаться.
У `cherry-pick` и `rebase` свои такие же — `CHERRY_PICK_HEAD`, `REBASE_HEAD`.

### Выйти, ничего не решая

```bash
git merge --abort
```

Дерево возвращается ровно в то состояние, что было до `pull`. Ничего
не потеряно. Это безопасная кнопка «отмена», и нажать её, если не понимаете,
что происходит, правильнее, чем править маркеры наугад.

У всех команд, которые умеют создавать конфликт, есть такой выход:
`git merge --abort` · `git cherry-pick --abort` · `git rebase --abort`.

### Разрешаем в VS Code

Над блоком с маркерами появляется строка кнопок:

| Кнопка | Что делает |
|---|---|
| **Accept Current** | оставить свой вариант (верхний блок, `HEAD`) |
| **Accept Incoming** | оставить чужой |
| **Accept Both** | оставить оба, друг за другом |
| **Compare Current Conflict** | открыть два варианта рядом |

Плюс `Accept All Current` / `Accept All Incoming` — на весь файл сразу,
и `Next Conflict` для файлов с десятком конфликтов.

Кнопка **`Resolve in Merge Editor`** открывает трёхпанельный редактор — про
расположение панелей см. [уточнение 1](#1-в-merge-editor-слева-ваш-вариант-а-не-чужой).

> ⚠️ **`Accept Both` — не универсальный ответ.** Она склеивает оба куска
> подряд. Для списка сьютов это правильно, а для изменённой строки кода даст
> две несовместимые строки, и файл перестанет компилироваться.

`git mergetool` настраивать не нужно: git 2.43 не знает VS Code как внешний
merge-инструмент (в `git mergetool --tool-help` его нет), и он не требуется —
VS Code сам видит маркеры в любом файле.

### Дорешиваем и коммитим

```bash
git add suites.txt                      # на конфликтном файле = «я разрешил»
git commit -m "слияние: оставил оба сьюта"
git cat-file -p HEAD | grep '^parent'   # две строки!
```

**У коммита слияния два `parent`** — это единственный вид коммита с двумя
родителями, и именно поэтому граф в этом месте сходится обратно. На уроке 8
у обычного коммита `parent` был один.

Если уже закоммитили неправильное разрешение — обычный `git revert`, как любой
коммит. До коммита — `git merge --abort`.

### Что с этим в `wl-e2e`

Три вещи, которые снимают половину страха:

- **Общие хелперы заморожены.** Tier-1 хелперы не редактируются, поэтому двое
  почти никогда не правят один файл.
- **Каждый работает в своём спеке.** Тест `C20992.spec.ts` правит один человек.
- **Есть ровно один файл, который сливать руками не нужно** —
  `.claude/mappings/testrail-code-map.json`: он генерируется скриптом, можно
  принять любую версию и перегенерировать.

А вот если конфликт всё же пришёлся на общий хелпер, автоматики нет: придётся
читать обе правки и понимать, какая из них что чинит. Тут не помогает ничто,
кроме внимательности, — и это нормально, конфликты разбираются медленно.

## `git worktree`

Пример: [`04-worktree.sh`](examples/04-worktree.sh)

```bash
git worktree add ../review ВЕТКА            # вторая папка с другой веткой
git worktree add -b ИМЯ ../pr-wt ОТКУДА     # сразу создать новую ветку
git worktree list                           # что у меня вообще есть
git worktree remove ../review               # убрать за собой
code -n ../review                           # открыть в новом окне VS Code
```

Две папки, **один репозиторий**, разные ветки одновременно. Это ответ на «как
поработать на другой ветке, не бросая свою работу»: не переключаться,
а завести вторую папку. Ничего не надо стэшить, открытые вкладки не меняются.

Одну ветку в двух рабочих деревьях сразу открыть нельзя:

```
fatal: 'main' is already used by worktree at '/tmp/.../sandbox'
```

Логично: иначе два места правили бы одну ветку и переписывали друг друга.

### Что в новую папку не приедет

Worktree выкладывает то, что **лежит в репозитории**. Всё, что в `.gitignore`,
туда не попадает по определению — его нет в истории. В `wl-e2e` это значит:

| Чего нет | Что делать |
|---|---|
| `node_modules/` | `yarn install` в новой папке (и `yarn.lock` на `draft` может быть другой) |
| `.env.*.secure` | скопировать руками: `cp` из основной папки |
| собранные образы, кэши | первый прогон будет дольше обычного |

Отсюда практическое: **прогнать тест в worktree перед PR стоит**. Там всплывёт
не только забытый конфиг, но и забытый общий хелпер, на который ваш тест
ссылается: сам тест вы перенесли, а хелпер — нет.

Убирать за собой нужно: рабочие деревья копятся, и через месяц их пять штук
по гигабайту.

## Как открывать PR на `draft`

Пример: [`05-pr-to-draft.sh`](examples/05-pr-to-draft.sh)

**Это главный практический блок обоих git-уроков.** Всё предыдущее было ради него.

### Расстановка сил

| Ветка | Роль |
|---|---|
| `autonomous-test-gen-experiment` | **рабочая.** Здесь чинятся и копятся тесты, сюда льют без спроса |
| `draft` | **только цель для PR.** Работать на ней нельзя |
| `AUT-{тикет}-C{кейс}-{описание}` | ветка под один PR, режется **от `origin/draft`** |

Насколько они разошлись:

```bash
git fetch origin draft
git rev-list --left-right --count origin/draft...HEAD
#  33   6208        ← замер 2026-09-10, числа живые
```

Читать по столбцам: левый — коммиты, которые есть только в `draft`, то есть
насколько рабочая ветка **отстаёт**. Правый — которые есть только у неё, то есть
насколько **опережает**.

Отставание в десятки, опережение в тысячи. Это не поломка — так устроен
эксперимент, и из порядка величин следует всё остальное. Числа не заучивайте:
левое ходит вверх-вниз (в `draft` вливаются PR-ы, ваши в том числе), правое
растёт непрерывно.

Синтаксис: три точки — «то, что есть у одной ветки и нет у другой, в обе
стороны», `--count` печатает количество вместо коммитов, `--left-right`
раскладывает его на два числа.

### Почему `cherry-pick` здесь не работает

Самое очевидное — перенести готовый коммит на ветку от `draft`. Не выйдет:

```
CONFLICT (content): Merge conflict in tests/base.ts
error: could not apply dc25ac1... AUT-1566: фикс поиска в Store
```

`cherry-pick` переносит **изменение**, то есть диф. А диф считается
относительно **родителя** коммита — и этого родителя на `draft` не существует,
там всё выглядит иначе. При расхождении в тысячи коммитов конфликт получается
сразу и на каждом файле.

Поэтому в `bugfix-batch.md` это записано **правилом 7: никогда не делать
`cherry-pick` на `draft`.** Не «нежелательно» — никогда.

### Как надо: worktree от `draft` + `git show`

Раз переносить изменение нельзя, переносим **содержимое файла**. Команда
знакома с [урока 8](../lesson-08/README.md#прочитать-файл-из-другого-коммита-не-переключаясь).

```bash
git worktree add -b AUT-1566-C20992-store-search ../pr-wt draft
cd ../pr-wt
git -C ../big show autonomous-test-gen-experiment:tests/C20992.spec.ts > tests/C20992.spec.ts
git add tests/C20992.spec.ts
git commit -m "AUT-1566: фикс поиска в Store (C20992)"
git diff --stat draft...HEAD
```

По шагам:

- **`git worktree add -b ИМЯ ПАПКА draft`** — завёл новую ветку от `draft`
  и сразу в отдельной папке. Рабочая ветка в основной папке не тронута.
- **`git -C ПУТЬ show ВЕТКА:ФАЙЛ > ФАЙЛ`** — достал содержимое файла из другой
  ветки и записал поверх. `-C` говорит «выполни git вон в той папке»: мы стоим
  в новом рабочем дереве, а читать надо из основного. Мышью, кстати, тоже
  можно — это обычные папки.
- **`git diff --stat draft...HEAD`** — то, что увидит ревьюер: один файл, одна
  строка. Три точки означают «от точки расхождения», то есть только ваше,
  без чужих коммитов.

**Три точки против двух** — единственный синтаксис, который стоит запомнить
отдельно:

```
draft..HEAD     коммиты, которых нет в draft
draft...HEAD    для diff: изменения относительно точки расхождения
```

В PR попадает второе.

### Настоящие команды процесса

Из `wl-e2e/.claude/commands/bugfix-batch.md`:

```bash
git fetch origin draft

git worktree add -b AUT-1566-C20992-store-search \
  /home/alex/work/wl-e2e-worktrees/AUT-1566-C20992 origin/draft
cd /home/alex/work/wl-e2e-worktrees/AUT-1566-C20992

git -C /home/alex/work/wl-e2e show \
  autonomous-test-gen-experiment:projects/monolith/tests/C20992.spec.ts \
  > projects/monolith/tests/C20992.spec.ts
git -C /home/alex/work/wl-e2e show \
  autonomous-test-gen-experiment:projects/monolith/tests/C20992.helpers.ts \
  > projects/monolith/tests/C20992.helpers.ts

yarn install
cp /home/alex/work/wl-e2e/projects/monolith/config/.env.staging-exp3.secure \
   projects/monolith/config/.env.staging-exp3.secure

yarn eslint projects/monolith/tests/C20992.spec.ts \
            projects/monolith/tests/C20992.helpers.ts

git add projects/monolith/tests/C20992.spec.ts \
        projects/monolith/tests/C20992.helpers.ts
git commit -m "AUT-1566: fix Store search for C20992"
git push -u origin AUT-1566-C20992-store-search
gh pr create --base draft --title "AUT-1566 C20992 ..." --body "..."

git worktree remove /home/alex/work/wl-e2e-worktrees/AUT-1566-C20992
```

Три места, где спотыкаются:

- **`yarn install` обязателен.** Ветка от `draft` — другой `yarn.lock`,
  и `node_modules` в новой папке своя.
- **`yarn eslint` до коммита, а не после.** Импорты на `draft` и на рабочей
  ветке разошлись: файл, который линтился на `experiment`, на `draft` может
  не пройти. Это ловят здесь, а не в PR.
- **`--base draft`** в `gh pr create` — без него PR уедет на ветку
  по умолчанию.

## Аутентификация и `gh`

В песочнице пароль не нужен, а на GitHub нужен. В `wl-e2e` адрес — HTTPS:

```
origin  https://github.com/wellnessliving/wl-e2e.git
```

Значит логин с паролем от аккаунта не сработает: GitHub их отключил. Нужен
токен — или, что проще, `gh`, который настроит git за вас:

```bash
gh auth login       # интерактивно: GitHub.com → HTTPS → браузер
gh auth status      # чем авторизованы сейчас
```

После `gh auth login` git берёт токен у `gh` сам, и `push` перестаёт
спрашивать. Альтернатива — SSH-ключ (`ssh-keygen -t ed25519`, публичную
половину в настройки GitHub, адрес переписать на `git@github.com:...`).

Ставить `gh` стоит и по другой причине: через него удобно открывать PR-ы,
читать их, добавлять описания и запускать прогоны из CI — и то же самое умеет
делать Claude, если `gh` установлен.

## `merge` против `rebase`

Пример: [`06-merge-vs-rebase.sh`](examples/06-merge-vs-rebase.sh)

Слово встретится в первый же рабочий день, поэтому знать надо. Применять
на проекте — нет.

```bash
git merge --no-edit main     # слить: сохранить обе ветки
git rebase main              # перенести свои коммиты поверх main
```

Результат в файлах одинаковый, история разная:

| | `merge` | `rebase` |
|---|---|---|
| история | ветвление сохранено | линейная, ветвления нет |
| новый коммит | коммит слияния с двумя родителями | нет |
| ваши коммиты | остаются как были | **создаются заново, с другими SHA** |

Последняя строка и есть главное:

> `rebase` не двигает коммиты, он создаёт новые вместо них. Отсюда единственное
> правило: **не делать `rebase` веток, которые уже на сервере и которые кто-то
> мог забрать.** У них останется старая версия, и дальше разойдётся всё.

Почему в `wl-e2e` `merge`: PR-ветка живёт часы и режется от свежего `draft` —
переписывать там нечего. А рабочую ветку с тысячами коммитов, которую забирают
все, ребейзить нельзя тем более.

## Панель «я всё сломал»

Сохранить и держать под рукой: этим пользуются в панике, когда искать конспект
некогда.

| Симптом | Что делать |
|---|---|
| **Не понимаю, что происходит** | `git status` — всегда первым. Git в нём сам пишет следующий шаг |
| Посреди конфликта, хочу выйти | `git merge --abort` |
| Посреди `cherry-pick` / `rebase` | `git cherry-pick --abort` / `git rebase --abort` |
| Надо срочно переключиться, правка не готова | `git stash push -u -m "черновик"` |
| Снёс коммит, он был нужен | `git reflog` → `git reset --hard HEAD@{N}` |
| Испортил файл, не коммитил | `git restore ФАЙЛ` — **вернуть будет нельзя** |
| Push отклонили | `git fetch` → `git status -sb` → смотреть `ahead/behind` |
| `HEAD detached` | `git switch -` |
| Коммит уже на сервере, надо отменить | `git revert <sha>` — **не** `reset` |
| Не помню, куда делся worktree | `git worktree list` |

**Одно правило поверх всех:** пока вы не сделали `git push`, испортить можно
только своё, и почти всё чинится. После `push` любое исправление видят все —
поэтому там только `revert`.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **`origin`** | имя для адреса удалённого репозитория. Не команда и не ключевое слово |
| **`origin/main`** | локальная копия указателя: где ветка сервера была при последнем `fetch`. Файл у вас на диске |
| **bare-репозиторий** | репозиторий без рабочей папки: только история. Так устроен сервер |
| **upstream** | удалённая ветка, к которой привязана локальная. Привязку ставит `push -u` |
| **`ahead` / `behind`** | на сколько коммитов ваша ветка впереди и позади удалённой |
| **конфликт слияния** | git не может решить, чей вариант оставить, потому что изменены соприкасающиеся куски |
| **коммит слияния** | коммит с двумя родителями, которым заканчивается `merge` |
| **`git worktree`** | вторая рабочая папка того же репозитория с другой веткой |
| **pull request (PR)** | предложение влить вашу ветку в целевую; у нас цель всегда `draft` |
| **`rebase`** | перенести свои коммиты поверх другой ветки, создав их заново |
| **`ort`** | стратегия слияния по умолчанию, «Ostensibly Recursive's Twin» |
