# Урок 17. Проект изнутри: устройство, запуск, Docker, CI

**Этот файл выложен до занятия: план тем и словарь.** Полный конспект
и домашка появятся здесь после урока.

Урок идёт **две встречи** — четверг 22.10 и пятница 23.10. В четверг
прошли блоки 1–5 (регрессию и гейт — на словах). Пятница — **Docker**,
основная тема: от первого контейнера до запуска тестов `wl-e2e`
в контейнере. Потом CI. Что не успеем — на следующей встрече.

Держите словарь открытым во время занятия.

## О чём урок

Два месяца мы смотрели на `wl-e2e` по одному файлу за раз. Теперь —
весь репозиторий: из каких частей он собран, через какие из них
проходит один тест, куда тест идёт и откуда там берутся данные, какие
команды есть в проекте, что проверяется перед PR — и что происходит
с тестом дальше: в Docker, в CI, в регрессии.

Урок практический: всё показываем запуском, а каждую часть — ещё
и тем, как она ломается.

**Три команды запустите у себя**, в своём `wl-e2e` — они ничего
не меняют и работают в Windows, macOS и Linux:

```bash
yarn workspaces list                          # из корня wl-e2e
yarn playwright test C19633 --list            # из projects/monolith
git ls-files config                           # из projects/monolith
```

**Файлы `.secure`** для окружений `staging-gen*` ведущий пришлёт архивом
в личку. В git их нет и не будет — никуда не пересылайте.

**Docker — подготовьте до пятницы.** На уроке почти все команды
повторяете у себя, поэтому без Docker будет только смотреть на экран.

1. Поставить Docker: Docker Desktop на Windows и macOS, Docker Engine
   и плагин `docker compose` на Linux. Проверка — `docker --version`
   и `docker compose version`.
2. Скачать два образа (вместе ~180 МБ, на уроке это съело бы время):

   ```bash
   docker pull node:24-alpine
   docker pull postgres:18-alpine
   ```

3. Обновить курс — `git pull`. Учебное приложение для Docker лежит
   в `lessons/lesson-17/runlog/`: маленький сервер на TypeScript. Ставить
   для него ничего не нужно — всё поставит Docker.
4. Для части про `wl-e2e` (скорее всего, уже следующая встреча) —
   образ Playwright, 3,4 ГБ:

   ```bash
   docker pull mcr.microsoft.com/playwright:v1.60.0-noble
   ```

   По желанию — собрать образ проекта, из корня своего `wl-e2e`
   (ещё ~4 ГБ на диске; учётки в образ не попадают):
   `docker compose -f docker-compose.dev.yml build monolith-dev`.

## План тем

| Блок | Тема | Что разберём |
|---|------|--------------|
| 1 | Карта проекта и установка | пять воркспейсов · что лежит в корне · установка по шагам: что делает каждая команда и что сломается без неё · как проверить, что всё настроено · как спек достаёт общий код: пакет `wl-e2e-automation-helpers` · шесть конфигов Playwright в одном проекте |
| 2 | Путь одного теста | `--list` и окружение по умолчанию · живой прогон через `yarn case` — что он делает за вас · кэш входа: `.auth/`, зачем он и как устроен · что вызывает тест: конфиг, окружение, константы, хелперы · спек, флоу, страница — куда класть новый код |
| 3 | Окружение: куда идёт тест | какие окружения живы · `.env` и `.env.secure` · что будет без `.secure` и как это читать · одна строка, из-за которой весь прогон находит ноль тестов · как проверить окружение, ничего не запуская |
| 4 | Откуда данные | паки `setup-run` · черновик окружения · «уже есть — не создавать второй» · «уже есть» — но с теми ли настройками? Ошибка, которую не ловит никто |
| 5 | Все команды проекта | 120 скриптов в пяти `package.json` — по группам · шаблон «окружение + конфиг» · какие команды никуда не ведут · `APP_ENV` в Windows и почему не делать `export` |
| 6 | Docker | зачем: «локальный зелёный — черновик» · образ, контейнер, том, сеть · чужие образы: Node и Postgres без установки · свой образ с нуля: `Dockerfile`, `docker build`, слои и кэш, размер образа · параметры запуска: порты, переменные, `--init` · тома: код с вашей машины, правка без пересборки · второй контейнер и сеть · `docker compose` · Docker в `wl-e2e`: образ Playwright, `Dockerfile` и `docker-compose.dev.yml` проекта, тесты в контейнере · оркестрация и пара слов о Kubernetes |
| 7 | CI | что GitHub Actions делает с вашим PR · гейт, поиск изменённых спеков, прогон на раннере в Docker · почему ваш PR сейчас упадёт на «Resolve developer secret» |

Регрессию и гейт в пятницу запуском не разбираем: гейт вы запустите
сами (домашка), регрессия — забота сервера QA.

Вопросы в пятницу будут заданы по именам. Подумать заранее можно над всеми:

1. Запустили контейнер, создали в нём файл, вышли. Запускаем новый
   контейнер из того же образа — файл там есть?
2. Сервер в контейнере слушает порт 3000, запустили с `-p 8080:3000`.
   Какой адрес открыть в браузере?
3. Удалили контейнер, к которому был подключён том. Что стало с томом?
4. Приложение и база — в двух контейнерах. Почему приложение
   не находит базу по адресу `localhost`?
5. `docker compose down` — данные базы пропали?

## Словарь терминов

Термины идут в порядке блоков: рядом с термином — номер блока, где он
появится; «чт, на словах» — прозвучали в четверг без запуска.

| Термин | Что значит |
|--------|------------|
| **воркспейс** (workspace) · 1 | папка со своим `package.json` внутри общего репозитория. Yarn ставит зависимости всем воркспейсам разом и связывает их. В `wl-e2e` их пять |
| **пакет** (package) · 1 | то, что импортируют **по имени**, а не по пути: `'@playwright/test'`, `'wl-e2e-automation-helpers/…'` |
| **флоу** (flow) · 2 | хелпер, который собирает действие из шагов нескольких страниц. Сам селекторов не пишет и ничего не проверяет |
| **пак** (pack) · 4 | папка в `setup-run/`: спеки, которые **создают** на бизнесе то, что нужно тестам, — бизнес, сотрудников, клиентов, настройки |
| **черновик окружения** · 4 | файл `config/.env.<env>.secure.draft`: туда пак пишет созданное, следующий спек пака читает оттуда. В `.secure` его переносит `yarn env:build` |
| **дорожка** (lane) · чт, на словах | часть полного прогона со своим набором спеков и числом воркеров: `parallel` — всё, кроме тестов, меняющих настройки бизнеса; `serial` — только они, по одному |
| **кластер** (cluster) · чт, на словах | группа примерно из ста спеков со своим бизнесом и своим окружением (`wl-aut-mt-c01`…). Тест, испортивший общие данные, портит их только соседям по кластеру |
| **гейт** (gate) · чт, на словах | одна команда, которая запускает все проверки проекта и говорит «можно / нельзя»: `yarn gate` |
| **база** (baseline) · чт, на словах | список старых нарушений, которые проверка пропускает. Новое нарушение сверх базы — ошибка |
| **образ** (image) · 6 | заготовка: система, программы, файлы. Сам не работает. Собирается по `Dockerfile` или скачивается готовым |
| **контейнер** (container) · 6 | запущенный образ. Из одного образа — сколько угодно контейнеров, каждый начинает с чистого листа |
| **реестр** (registry) · 6 | сервер, где хранят образы и откуда их скачивают: Docker Hub, `mcr.microsoft.com` |
| **тег** (tag) · 6 | версия образа, после двоеточия: `node:24-alpine` |
| **Dockerfile** · 6 | рецепт образа: шаги сверху вниз — `FROM`, `COPY`, `RUN`, `CMD` |
| **том** (volume) · 6 | папка, которую Docker подключает к контейнеру и которая живёт отдельно от него: папка вашей машины или именованное хранилище Docker |
| **сеть** (network) · 6 | внутри своей сети контейнеры находят друг друга по имени |
| **сервис** (service) · 6 | один контейнер в `compose.yaml` со всеми его настройками |
| **слой** (layer) · 6 | результат одного шага `Dockerfile`. Образ — стопка слоёв; неизменившиеся слои Docker берёт из кэша |
| **оркестрация** · 6 | когда за контейнерами следит программа: порядок запуска, готовность, перезапуск упавших |
| **воркфлоу** (workflow) · 7 | файл в `.github/workflows/`: на какое событие (PR, кнопка) что запускать |
| **раннер** (runner) · 7 | машина, на которой GitHub выполняет воркфлоу: своя у GitHub или своя у компании |
