## Уточнения к занятию

Места, где на занятии прозвучала неточность. Всё проверено запуском.

**1. От интерфейса не наследуются — ему соответствуют.** Класс с
`implements X` ничего от `X` не получает: каждый метод договора он пишет
сам. Наследуют только от класса, через `extends`.

**2. Интерфейс и класс — не взаимозаменяемы, и дело не
в мультипарадигменности JavaScript.** В чисто объектных языках (Java, C#)
интерфейсы тоже есть. Разница — в разделе
[«Интерфейс, абстрактный класс и класс»](#интерфейс-абстрактный-класс-и-класс).

**3. Почему в проекте не пишут классы-страницы, в документации проекта не
записано.** Записано другое: хелперы-страницы — это файлы `…-page.ts`
с функциями, и новый хелпер пишется так же, как соседние. Что функции
дают и чего не дают — в разделе [«ООП и наш проект»](#ооп-и-наш-проект).
Playwright page object тоже не требует: в его документации это «один из
подходов» к устройству тестов.

**4. `this` внутри статического метода есть — это сам класс.** Поэтому
статический метод не может работать с полями экземпляра: у самого класса
поля `page` нет (`TS2339`).

**5. `Error` кладёт в экземпляр `message` и `stack`, но не `name`.**
`name` лежит в `Error.prototype`. Поэтому у пустого наследника имя
`'Error'`, а `OverlapRefusal` записывает своё сам.

**6. `super` — не метод, а ключевое слово:** «звено выше». `super(...)`
в конструкторе вызывает конструктор **родителя**, `super.метод()` —
метод родителя.

**7. Тип `Promise<void>` у асинхронной функции не обязателен.** TypeScript
выведет его сам: `async function save() { … }` и так возвращает
`Promise<void>`. В хелперах `wl-e2e` его обычно пишут явно (так —
у всех четырёх функций `client-note-page.ts`), но обязательным правило X1
из `RULES.md` делает его, только когда в асинхронной функции есть условный
ранний `return`.

**8. Классов в проекте три, а не один:** `TestRailReporter` и два класса
ошибок — `OverlapRefusal` и `AchProvisioningGap`.

Поправки к уроку 13 — в его [конспекте](../lesson-13/README.md#уточнения-к-занятию):
в первую очередь пункт 1, «общий массив в прототипе — ошибка, а не приём».

## Что такое ООП

**Объектно-ориентированное программирование** — методология
программирования, основанная на представлении программы в виде
совокупности **объектов**, каждый из которых является экземпляром
определённого **класса**, а классы образуют **иерархию наследования**
(определение Гради Буча).

JavaScript — язык не только объектный: на нём пишут и функциями, и
в других стилях. Классы в нём — запись поверх прототипов (урок 13), а
объект можно создать вообще без класса, литералом. Определение от этого
не ломается: объекты, их общее поведение и наследование — на месте.

Объект держит **вместе** данные и то, что с ними делают. Локатор помнит,
что искать, — данные — и умеет `click`, `count`, `first` — поведение.
Так написан весь Playwright.

Четыре принципа, на примере автомобиля с автоматической коробкой:

| Принцип | Формально | В машине |
|---|---|---|
| **Инкапсуляция** | данные и методы, работающие с ними, — в одном объекте, внутреннее устройство скрыто | у вас две педали — газ и тормоз. Коробка передач переключается сама, вмешаться в неё нельзя |
| **Наследование** | новый класс описывается на основе существующего и получает его свойства и методы | — |
| **Полиморфизм** | объекты разных классов отвечают на один и тот же вызов по-своему | ключ зажигания поворачивается одинаково в любой марке, а заводится каждый двигатель по-своему |
| **Абстракция** | важно, **что** объект умеет, а не **как** устроен | неважно, какой двигатель — бензиновый, дизельный, V8; важно, что он даёт крутящий момент |

## Инкапсуляция

Пока поле класса открыто, его можно поменять снаружи, мимо методов:

```ts
const open = new OpenAttempts();
open.next();
open.used = -100;
open.next();   // 'попытка -99'
```

Счётчик врёт и сам об этом не знает. `private` закрывает поле: менять его
могут только методы самого класса, а `attempts.used = -100` снаружи —
`TS2341`. Следит за этим только TypeScript; настоящая приватность
в JavaScript пишется `#used`.

### Геттер или обычный метод

Чтобы прочитать спрятанное значение, способов два:

```ts
class CountedAttempts {
  private used = 0;
  next() { this.used += 1; }
  count() { return this.used; }      // обычный метод: counted.count()
  get spent() { return this.used; }  // геттер: counted.spent — без скобок
}
```

**Геттер** — функция, которая вызывается, когда свойство **читают**. Снаружи
он выглядит как обычное свойство: `typeof counted.spent` — `number`.
Присвоить ему нельзя (`TS2540`). Геттеры бывают и у объектов-литералов,
не только у классов.

**Зачем геттер, если есть метод?** Разницы в скорости нет — только в записи.
Чаще всего метода достаточно. Геттер нужен, когда значение должно
**выглядеть как данные**. В проекте два таких случая:

1. **Вычисляемое поле не устаревает.** У `FILLER` в `C21173.helpers.ts`
   имя — геттер `get name() { return \`${this.first} ${this.last}\`; }`.
   Обычное поле собиралось бы один раз и расходилось с `first`/`last`
   после правки. А читают его так же, как остальные данные клиента:
   `SUBJECT.name` рядом с `SUBJECT.uid`.
2. **Объект подходит туда, где ждут данные.** Хелпер
   `updateRelationshipClientDob` (`C58238.helpers.ts`) принимает
   `{ email: string; ageYears: number }`. У `REL1` в спеке `email` — геттер,
   и для хелпера это строка. Будь это метод `email()`, объект под тип
   не подошёл бы (`TS2345`): пришлось бы переписывать хелпер и каждое
   место, где читают `rel.email`. А зачем там вообще не обычное поле,
   написано в комментарии над `REL1`: значение берётся **в момент
   чтения**. Адрес достаётся из фикстуры стенда, и если её нет, ошибка
   случится внутри теста, а не при импорте файла.

### Сеттер

**Сеттер** — функция, которая вызывается, когда свойству **присваивают**:

```ts
class RetryLimit {
  private value = 3;
  get limit() { return this.value; }
  set limit(next: number) {
    if (next < 1) throw new Error(`limit must be positive, got ${next}`);
    this.value = next;
  }
}
retry.limit = 5;   // сработал сеттер
retry.limit;       // сработал геттер — 5
retry.limit = 0;   // сеттер бросил ошибку
```

Одно имя работает в обе стороны. Вместе с `private` это инкапсуляция
целиком: данные спрятаны, единственная дверь к ним — с проверкой на
входе. Своих сеттеров в проекте нет; чужим пользуетесь постоянно —
`input.value = 'Yoga'` в браузере это сеттер.

Пример — [`01-encapsulation.ts`](examples/01-encapsulation.ts).

## Наследование

```ts
class ListReporter {
  mark(status: string): string { return status === 'passed' ? '✓' : '✘'; }
  onTestEnd(caseId: string, status: string) { return `${this.mark(status)} ${caseId}`; }
}
class WidgetsListReporter extends ListReporter {
  project = 'widgets';
}
```

`class B extends A` — наследник получает поля и методы родителя
и дописывает свои. Устроено цепочкой прототипов на звено длиннее
(урок 13).

**Переопределение** — метод с тем же именем в наследнике:

```ts
class DotReporter extends ListReporter {
  mark(status: string) { return status === 'passed' ? '·' : 'F'; }
}
new ListReporter().onTestEnd('C157112', 'passed');   // '✓ C157112'
new DotReporter().onTestEnd('C157112', 'passed');    // '· C157112'
```

`onTestEnd` написан один раз, в родителе. Внутри него `this.mark(...)`,
а `this` — объект, у которого вызвали метод. У `DotReporter` свой
`mark` — он и сработал. **Код родителя вызвал метод наследника, ничего
о нём не зная.** Настоящие `--reporter=list` и `--reporter=dot` печатают
те же значки: `list` — `✓`/`✘` со строкой теста, `dot` — одни точки и `F`.

**`super.метод()`** — вызвать метод родителя, чтобы дописать к нему,
а не заменить: `` `${super.onTestEnd(caseId, status)} (${status})` ``.

**`super(...)` в конструкторе** — вызвать конструктор родителя.
Единственный `constructor` в проекте — у ошибки `OverlapRefusal`
(`C94015.helpers.ts`):

```ts
class OverlapRefusal extends Error {
  constructor(diagnostics: string) {
    super(`the checkout refused this session … ${diagnostics}`);
    this.name = 'OverlapRefusal';
  }
}
```

Правило жёсткое: **`super(...)` раньше первого `this`** — объект создаёт
самый верхний конструктор, и до его вызова `this` нет.

Пример — [`02-inheritance.ts`](examples/02-inheritance.ts).

## Полиморфизм

```ts
const reporters = [new ListReporter(), new DotReporter(), new TestRailLikeReporter()];
for (const reporter of reporters) reporter.onTestEnd('C157112', 'passed');
// '✓ C157112' · '· C157112' · 'C157112 → TestRail'
```

Цикл не знает, кто перед ним, — он зовёт `onTestEnd`, и каждый объект
отвечает по-своему. Третий репортер ничей не наследник: для полиморфизма
в JavaScript достаточно метода с тем же именем.

Ровно так Playwright работает со списком `reporter` в конфиге проекта:
`list`, `allure-playwright`, наш TestRail-репортер — после каждого теста
он зовёт `onTestEnd` у каждого. И так же вы работаете с ошибками: у
любого наследника `Error` есть `name` и `message`, поэтому
`e instanceof Error ? e.message : String(e)` подходит для всех.

## Абстракция

```ts
interface CaseReporter {
  onTestEnd(caseId: string, status: string): string;
}
const runAll = (items: CaseReporter[]) => items.map((item) => item.onTestEnd('C157112', 'passed'));
```

`CaseReporter` — договор: «у меня есть `onTestEnd` с такими параметрами».
Кода в нём нет. `runAll` написана под договор, а не под конкретный класс.
`implements CaseReporter` требует методы договора — и не запрещает свои.

**`abstract class`** — договор, в котором часть кода уже есть. Создать его
через `new` нельзя (`TS2511`), только унаследовать; методы с `abstract`
наследник обязан написать. В проекте `abstract` нет.

### Интерфейс, абстрактный класс и класс

Вопрос с занятия: зачем интерфейс, если есть классы? Коротко: интерфейс —
это **тип**, класс — это **код**.

| | `interface` | `abstract class` | `class` |
|---|---|---|---|
| код методов | нет | частично | весь |
| есть при запуске программы | нет | да | да |
| можно сделать `new` | нет (`TS2693`) | нет (`TS2511`) | да |
| сколько на один класс | `implements A, B` — сколько угодно | `extends` — один (`TS1174`) | `extends` — один |

Интерфейсу соответствует что угодно подходящей формы: класс,
объект-литерал, объект чужой библиотеки. Поэтому `Reporter` в Playwright —
интерфейс: наш `TestRailReporter` ему соответствует, ничего от Playwright
не наследуя.

Пример — [`03-polymorphism-abstraction.ts`](examples/03-polymorphism-abstraction.ts).

## ООП и наш проект

Одна «страница» в двух записях:

```ts
// у нас: функции, page — первым параметром
const saveNote = (page: Page, text: string) => { … };

// «page object» из учебников: page — в поле экземпляра
class ClientNotePage {
  private readonly page: Page;
  constructor(page: Page) { this.page = page; }
  save(text: string) { … }
}
```

Результат один и тот же. Разница — **где живёт `page`**. Своих данных
у страницы нет, всё состояние — в браузере.

Что из ООП даёт обычный файл-модуль вроде `client-note-page.ts`:

| Принцип | В классе | В модуле |
|---|---|---|
| инкапсуляция | `private` | константы и функции **без `export`** видны только внутри файла |
| публичное | методы без `private` | функции с `export` |
| абстракция | договор `interface` | тест зовёт `saveFlaggedClientNote(page, …)` и не знает ни одного селектора |
| наследование | `extends` | не нужно: общее выносят в функцию |
| полиморфизм | один вызов — разные классы | не нужен: у страницы одна реализация |

**Класс нужен там, где у объекта есть своё состояние между вызовами**,
которое не приходит параметром. `TestRailReporter` помнит `enabled`,
`runId` и `results` от `onBegin` до `onEnd` — ему класс нужен. `page`
помнит вкладку, локатор — что искать. Хелперу страницы помнить нечего.

Page object классами — не ошибка, а другая запись того же самого. В нашем
проекте принята запись функциями, и новый хелпер пишется так же, как
соседние.

### Статические методы

`Object.keys`, `Array.from`, `Date.now` — методы самого класса, без
экземпляра. Пишутся со словом `static`; `this` внутри — сам класс.
Поэтому статический метод не работает с полями экземпляра. Своих `static`
в проекте нет.

Пример — [`04-oop-in-our-project.ts`](examples/04-oop-in-our-project.ts).

## Итог занятия

1. ООП — программа из объектов; объект держит вместе данные и то, что
   с ними делают. Четыре принципа: инкапсуляция, наследование,
   полиморфизм, абстракция.
2. **Инкапсуляция** — `private`, геттер, сеттер. Геттер нужен, когда
   значение должно выглядеть как данные; иначе хватает метода.
3. **Наследование** — `extends`; код родителя зовёт переопределённый метод
   наследника; `super(...)` — раньше первого `this`.
4. **Полиморфизм** — один вызов, разное поведение: список репортеров,
   любые ошибки как `Error`.
5. **Абстракция** — работа через договор; `interface` — тип без кода,
   ему соответствуют, а не наследуют.
6. Класс нужен там, где есть состояние между вызовами. Репортеру — да,
   хелперу страницы — нет.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **инкапсуляция** (encapsulation) | данные и методы, которые с ними работают, собраны в одном объекте, а внутреннее устройство скрыто: менять данные можно только его собственными методами |
| **геттер** (getter) | функция, которая вызывается, когда свойство читают. Пишется `get имя() { … }`, читается без скобок |
| **сеттер** (setter) | функция, которая вызывается, когда свойству присваивают. Пишется `set имя(значение) { … }`, вызывается знаком `=` |
| **наследование** (inheritance) | новый класс описывается на основе существующего: `class B extends A`. Наследник получает поля и методы родителя и дописывает свои |
| **переопределение** (override) | метод с тем же именем в классе-наследнике. Вызывается он, а не родительский |
| **полиморфизм** (polymorphism) | объекты разных классов отвечают на один и тот же вызов по-своему |
| **абстракция** (abstraction) | выделить в объекте существенное и отбросить остальное: важно, что он умеет, а не как устроен |
| **статический метод** (static method) | метод самого класса, а не экземпляра: `Array.from(...)`, `Date.now()` |
