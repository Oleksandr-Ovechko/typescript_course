## Уточнения к занятию

**1. `some` возвращает `true` или `false`, а не элемент.** Элемент возвращает
`find`. И `some`/`every` не новые — они в языке с 2009 года (ES5).

**2. `for...in` отдаёт только ключи.** Прозвучало «сразу ключ и значение»,
и на экране была запись `for (const {key, value} in timeouts)`. Она
не компилируется (`TS2491`), а в JavaScript даёт `undefined`: `for...in`
отдаёт строку `'short'`, и полей `key`/`value` у неё нет. С квадратными
скобками `[key, value]` получаются **первые две буквы ключа** — строка
итерируема. Пара «ключ — значение» — это
`for (const [key, value] of Object.entries(obj))`.

**3. В JavaScript не всё — объекты.** Семь примитивов (урок 1) объектами
не являются. Массивы — являются.

**4. `Array.from` не старше спреда.** Оба появились в 2015 году (ES2015),
вместе с `for...of`, `Symbol` и генераторами. Старая форма — это
`Array.prototype.some.call(список, …)`. А причина, по которой в проекте
пишут `Array.from`, — не привычка, а версия TypeScript и конфиг:
[отдельный раздел ниже](#почему-в-проекте-arrayfrom-а-не-спред).

**5. Спред и `Array.from` умеют разное.** Спред берёт только итерируемое.
`Array.from` — и итерируемое, и просто массивоподобное. На массивоподобном
без итератора TypeScript ругается только на спред (`TS2488`), `Array.from`
компилируется.

**6. `Symbol` — не «недавно» и не про память.** Он появился в ES2015, и нужен
он, чтобы получить ключ свойства, **который не совпадёт ни с одной строкой**.
Подробно — в [«Что такое символ»](#что-такое-символ).

**7. `Symbol.iterator` лежит не в самом массиве, а в его прототипе** — общем
месте для всех массивов. Как это устроено, разберём на уроке про прототипы.

**8. Генераторы тоже не «очень недавние»** — ES2015.

**9. `rest` после деструктуризации — это значения итератора, а не свойства
объекта.** В `const [first, ...rest] = attempts` у `rest` два элемента,
потому что итератор отдал три значения и первое забрал `first`. Свойства
`limit` там тоже нет — деструктуризация свойства вообще не смотрит.

**10. `done: true` со значением — это `return`, а не «особенность
генераторов».** Итератор, написанный руками, тоже может вернуть
`{ value: 'ИТОГ', done: true }`, и спред это значение так же выбросит.
И третий `next()` у `withReturn` отдаёт одно значение `'ИТОГ'`, а не
«все оставшиеся».

**11. `*[Symbol.iterator]()` — не безымянный метод.** Это метод с
**вычисляемым именем**: имя — значение `Symbol.iterator`.

**12. Асинхронный генератор не работает «параллельно».** Он так же ленив,
как обычный: тело не начнётся, пока не попросили `next()`.

**13. `for await` в `C139796.helpers.ts` не нужно «переписывать на
генераторы».** Поток уже умеет отдавать куски по одному — `for await`
пользуется тем же протоколом. А в память файл попадает целиком намеренно:
сразу после цикла стоит `Buffer.concat(chunks)`, потому что календарный файл
разбирается целиком. Генератор тут ничего бы не изменил.

**14. Обычный `for` — самый быстрый, а не самый медленный.** Цепочка
`filter → map → reduce` на десяти миллионах элементов в 17 раз медленнее,
генератор — вдвое медленнее `for...of`. Таблица — в [«Что быстрее»](#что-быстрее).

И мелочь: `while (true)` с пустым телом не переполняет память — он просто
занимает процессор и не даёт выполниться ничему другому.

## Циклы

### Счётчик и потолок

```ts
for (let attempt = 0; attempt < LIMIT; attempt++) { … }
```

Три части заголовка выполняются в разное время:

| Часть | Когда |
|---|---|
| `let attempt = 0` | один раз, до первого прохода |
| `attempt < LIMIT` | **перед** каждым проходом; `false` — цикл закончен |
| `attempt++` | **после** каждого прохода |

`let`, а не `const`, потому что `attempt++` меняет переменную (урок 4).

В проекте почти каждый такой цикл — **ретрай с потолком**: повторить действие
не больше N раз и выйти, как только получилось. Например,
`helpers/monolith/client-profile/add-relationship-page.ts` трижды повторяет
поиск клиента, потому что только что созданный клиент появляется в поиске
с задержкой. Потолок обязателен (правило W7, пункт b, в `RULES.md`): без него тест не падает,
а зависает — и умирает по таймауту с бесполезным сообщением вместо трейса.

### Цикл без счётчика

`while (условие)` крутится, пока условие истинно. Берут его, когда число
проходов заранее неизвестно. В проекте их около шестисот против девяти тысяч
`for` — и это правильное соотношение: у теста почти всегда должен быть
потолок. `while (true)` без `break` внутри — это зависший тест.

### Прервать проход или весь цикл

- `continue` — закончить **этот** проход и перейти к следующему;
- `break` — выйти из цикла совсем.

```ts
for (const code of ['C157112', 'skip', 'C22041', 'C19877']) {
  if (code === 'skip') continue;   // этот пропустили, едем дальше
  if (taken.length === 2) break;   // набрали два — хватит
  taken.push(code);
}
// taken: [ 'C157112', 'C22041' ]
```

### Конструкция языка против вызова функции

```ts
suites.forEach((s) => { if (s === 'monolith') return; });   // прошёл все три
for (const s of suites) { if (s === 'monolith') break; }     // остановился на втором
```

`forEach` — это **вызов функции** на каждый элемент. `return` внутри выходит
из этой функции, а не из перебора; остановить `forEach` нечем, `break` там
даже не скомпилируется.

`for...of` — **конструкция языка**. Поэтому в нём работают `break`,
`continue` и — главное для тестов — `await`: тело цикла принадлежит той же
асинхронной функции и честно её тормозит. Так устроен каждый цикл по
локаторам в проекте:

```ts
for (const label of await page.locator('label.css-rs-form-week-select-list').all()) {
  const input = label.locator('input[name="a_day[]"]');
  if (!(await input.isChecked())) {
    await label.click();
  }
}
```

С `forEach` на этом месте тест не упадёт — он молча пойдёт дальше
по недокликанной форме. Подробно — урок 5,
[`05-forgotten-await.ts`](../lesson-05/examples/05-forgotten-await.ts).

### Ранний выход без цикла

Если нужен не сам элемент, а ответ «есть ли такой» — цикл не нужен:

- `some(fn)` — `true` на первом совпадении, дальше не смотрит;
- `every(fn)` — `false` на первом несовпадении, дальше не смотрит;
- `find(fn)` — сам первый подходящий элемент или `undefined`.

`some` и `every` возвращают **`true`/`false`**, не элемент. За элементом —
`find`.

### Перебор объекта

У объекта три способа, и в проекте живёт один:

| Запись | Что даёт | В проекте |
|---|---|---:|
| `for (const [key, value] of Object.entries(obj))` | пару ключ — значение | ~170 |
| `for (const key of Object.keys(obj))` + `obj[key]` | ключ, значение — отдельным обращением | есть |
| `for (const key in obj)` | **только ключ**, строкой | 0 |

`for...in` перебирает ключи. У массива ключи — индексы, и они **строки**:
`for (const k in ['a', 'b'])` даёт `'0'`, `'1'`, а не `0`, `1` и не `'a'`.
Поэтому по массиву `for...in` не ходят. Знать его нужно, чтобы узнавать
в чужом коде.

> По массиву — `for...of`. По объекту — `Object.entries`.

## Что делает объект перебираемым

### Перебрать можно, методов массива нет

В проекте ~2 300 `Array.from`, и почти все — над DOM-коллекциями, внутри
`page.evaluate`:

```ts
Array.from(select.options)
Array.from(document.querySelectorAll<HTMLInputElement>('input.js-cell-phone'))
```

`select.options` — это `HTMLOptionsCollection`, `querySelectorAll` отдаёт
`NodeList`. Оба можно увидеть самим: в DevTools навести на элемент, и в
консоли он доступен как `$0` — `$0.options`.

Это не массивы. У них есть `length` и числовые индексы — такой объект
называется **массивоподобным**. И в браузере оба **итерируемы**: `for...of`
и спред по ним работают. Нет у них другого — **методов массива**: ни `map`,
ни `filter`, ни `find`. (`forEach` у `NodeList` как раз есть, у
`HTMLOptionsCollection` — нет.)

Итерируемость и методы массива — два независимых свойства:

| | итерируемый | массивоподобный | методы массива |
|---|:---:|:---:|:---:|
| массив | ✅ | ✅ | ✅ |
| `NodeList`, `HTMLOptionsCollection` | ✅ | ✅ | ❌ |
| `{ length: 2, 0: 'a', 1: 'b' }` | ❌ | ✅ | ❌ |
| строка, `Set`, `Map` | ✅ | строка — да | ❌ |

`Array.from` умеет делать массив из **обоих** видов: ему хватает `length`
и числовых ключей. Спред — только из итерируемого:

```ts
Array.from({ length: 2, 0: 'первый', 1: 'второй' })   // [ 'первый', 'второй' ]
[...arrayLike]                                         // ❌ TS2488, в рантайме TypeError: not iterable
Array.from({ length: 3 }, (_, i) => `попытка ${i + 1}`) // идиома «массив из N элементов»
```

Второй аргумент `Array.from` — функция-преобразователь: вызывается на каждом
элементе, первый параметр — сам элемент (здесь его нет, поэтому `_`),
второй — индекс.

### Почему в проекте `Array.from`, а не спред

На уроке прозвучал вопрос: `Array.from` — старый способ, почему не
`[...список]`? Ответ зависит от того, **какой TypeScript проверяет код**,
и здесь у вас их два.

В `tsconfig.json` проекта стоит:

```json
"lib": ["ES2022", "DOM"]
```

| Кто проверяет | Версия | `[...nodeList]`, `for...of` по `NodeList`, `[...select.options]` |
|---|---|---|
| `yarn typecheck` в проекте и в курсе | TypeScript **5.9** из `node_modules` | ❌ `TS2488` |
| VS Code — подсветка в редакторе | TypeScript **6.0**, встроенный в редактор | ✅ ошибки нет |

До версии 6.0 итерируемость DOM-коллекций описывалась отдельной библиотекой
`"DOM.Iterable"`, и при нашем `lib` её нет — для TypeScript 5.9 `NodeList`
и `options` **не итерируемы**, хотя в браузере итерируемы. В 6.0 её влили
в `"DOM"`, и та же строка стала законной. Редактор VS Code по умолчанию
берёт свой встроенный TypeScript, а не версию проекта, — поэтому в редакторе
красного нет, а `yarn typecheck` падает.

`Array.from` принимает любое массивоподобное, итератор ему не нужен, — поэтому
он компилируется **под обеими версиями**. Отсюда и выбор проекта: запись,
которая проходит проверку при любом TypeScript. Все строки воспроизводятся
в [`02-iterable-and-array-like.ts`](examples/02-iterable-and-array-like.ts):
`yarn typecheck` покажет ошибку, редактор — нет.

> **Урок шире темы.** «Редактор не подчёркивает» и «проверка проходит» —
> разные утверждения. Что попадёт в PR, решает `yarn typecheck`. Чтобы
> редактор показывал то же самое, в VS Code: `Ctrl+Shift+P` →
> «TypeScript: Select TypeScript Version» → «Use Workspace Version».

> ⚠️ На рабочей ветке спредов по DOM-коллекциям больше сотни, все
> в `projects/monolith` — видимо, написаны, глядя на редактор. Для
> `yarn typecheck` каждый из них — `TS2488`. Проверка их сейчас не видит
> и сама: `tsc` не переходит к проверке типов, пока в проекте есть
> синтаксическая ошибка, а она есть в другом файле. Урок отсюда общий:
> **чистый вывод `tsc` при синтаксической ошибке ничего не говорит о типах**.

По возрасту обе записи одинаковы: и `Array.from`, и спред появились
в ES2015. Действительно старая форма — `Array.prototype.some.call(список, fn)`:
взять метод у массивов и вызвать его на чужом объекте (`call` — урок 6).
В проекте такая одна.

### Протокол итератора

«Умеет отдавать элементы по одному» — не метафора, а конкретный метод:

```ts
const it = suites[Symbol.iterator]();
it.next();   // { value: 'widgets', done: false }
it.next();   // { value: 'monolith', done: false }
it.next();   // { value: 'explorer', done: false }
it.next();   // { value: undefined, done: true }
```

У массива есть метод под ключом `Symbol.iterator`. Он возвращает
**итератор** — объект с методом `next()`. Каждый `next()` отдаёт
`{ value, done }`. Обратите внимание: последний элемент приходит ещё
с `done: false`, и только следующий вызов говорит `done: true`.

Договорённость «есть метод `[Symbol.iterator]`, возвращающий итератор» —
это **протокол итератора**. `for...of` не делает ничего сверх неё:
получает итератор и вызывает `next()`, пока не придёт `done: true`.

### Свой перебираемый объект

Раз это договорённость, её можно выполнить самому:

```ts
const attempts = {
  limit: 3,
  [Symbol.iterator](): Iterator<string> {
    let n = 0;
    return {
      next: () =>
        n < this.limit
          ? { value: `попытка ${++n}`, done: false }
          : { value: undefined, done: true },
    };
  },
};
[...attempts];   // [ 'попытка 1', 'попытка 2', 'попытка 3' ]
```

Обычный объект, не массив, — а спред работает. Четыре знакомые вещи:

| Кусок | Что делает |
|---|---|
| `[Symbol.iterator]()` | метод с **вычисляемым именем**: в скобках значение, а не строка |
| `return { next: … }` | метод обязан вернуть итератор — объект с `next` |
| `n < this.limit ? … : …` | тернарник: остались попытки — значение, нет — `done: true` |
| `${++n}` | сначала увеличить, потом подставить; с `n++` первой была бы «попытка 0» |

`n` живёт в **замыкании** (урок 6): каждый вызов `[Symbol.iterator]()`
заводит свой счётчик, поэтому объект можно перебрать дважды, и оба раза
с начала. `this.limit` — это `attempts`, потому что метод вызван через него.

### Один протокол, четыре записи

```ts
for (const a of attempts) {}          // for...of
[...attempts]                          // спред
const [first, ...rest] = attempts;     // деструктуризация массива
Array.from(attempts)                   // Array.from
```

Все четыре — один и тот же протокол. Строка итерируема (отсюда `[...str]`
и правильный счёт эмодзи из урока 4), `Set` итерируем (отсюда
`[...new Set(x)]` для удаления повторов).

## Генераторы

### Функция, которая умеет замирать

Писать итератор руками — десять строк ради трёх значений. Короткая запись:

```ts
function* attemptNames(limit: number): Generator<string> {
  for (let n = 1; n <= limit; n++) yield `попытка ${n}`;
}
[...attemptNames(3)];   // [ 'попытка 1', 'попытка 2', 'попытка 3' ]
```

Звёздочка после `function` делает функцию **генератором**. При вызове тело
не выполняется — возвращается итератор. На каждый `next()` тело идёт до
ближайшего `yield`, отдаёт значение и **замирает** на этом месте до
следующего `next()`.

Генератор — это вся функция, а не цикл внутри неё. `for` в примере — просто
способ отдать три значения; можно написать три `yield` подряд.

```ts
const g = attemptNames(2);
g.next();   // { value: 'попытка 1', done: false }
g.next();   // { value: 'попытка 2', done: false }
g.next();   // { value: undefined, done: true }
```

Тот же `{ value, done }`, что у массива: генератор — не новая сущность,
а короткая запись того же протокола.

### Что делает `return` в генераторе

```ts
function* withReturn(): Generator<string, string, unknown> {
  yield 'первый';
  yield 'второй';
  return 'ИТОГ';
}
```

`next()` вручную: `первый` → `второй` → `{ value: 'ИТОГ', done: true }`.
Спред: `[ 'первый', 'второй' ]` — без `ИТОГ`.

`return` приходит **вместе с `done: true`**, а всё, что перебирает
(`for...of`, спред, `Array.from`, деструктуризация), значение с
`done: true` выбрасывает. Это правило протокола, а не генераторов:
рукописный итератор с `{ value: 'ИТОГ', done: true }` ведёт себя так же.
Вывод: данные отдают через `yield`.

Если выйти из `for...of` по `break`, генератор **закрывается**: если внутри
стоял `try/finally`, `finally` выполнится.

### Ленивость

```ts
function* forever(): Generator<number> {
  let n = 0;
  while (true) yield (n += 1);
}
for (const n of forever()) { if (n > 4) break; few.push(n); }   // [ 1, 2, 3, 4 ]
```

Не зависает. `while (true)` внутри генератора не крутится сам по себе:
он делает **один шаг на каждый запрос** и замирает на `yield`. Никто
не спросил — ничего не считается. Это и есть **ленивое вычисление**.

А вот `[...forever()]` повесит процесс: спред просит **все** значения.

Отсюда и единственный настоящий довод за генератор: значение дорого
считать, и неизвестно, сколько их понадобится. Посчитается ровно столько,
сколько попросили.

### Генератор как метод объекта

```ts
const suite = {
  cases: ['C157112', 'C22041', 'C19877'],
  *[Symbol.iterator](): Generator<string> {
    for (const c of this.cases) yield `[${c}]`;
  },
};
[...suite];   // [ '[C157112]', '[C22041]', '[C19877]' ]
```

То же, что «свой перебираемый объект», но в три строки. Читается
как «метод с именем `Symbol.iterator`, который является генератором строк»:
`*` — генератор, `[Symbol.iterator]` — вычисляемое имя, `Generator<string>`
уже итератор, так что протокол выполнен.

### Асинхронный перебор

Своих генераторов в проекте нет, а **асинхронный перебор** есть — семь мест,
и все читают скачанный файл. Вот одно, из
`projects/widgets/…/C139796.helpers.ts` (на рабочей ветке; на `draft`
этого файла нет):

```ts
const stream = await download.createReadStream();
const chunks: Buffer[] = [];
for await (const chunk of stream) {
  chunks.push(Buffer.from(chunk));
}
// … Buffer.concat(chunks).toString('utf8')
```

`for await...of` — тот же протокол, только `next()` возвращает **промис**
`{ value, done }`, и цикл дожидается каждого. Поток из Node такой протокол
уже выполняет (у него есть метод `Symbol.asyncIterator`), поэтому
по нему можно идти `for await` без всяких обёрток. Куски приходят по мере
чтения — а здесь их потом склеивают в одну строку, потому что календарный
файл разбирается целиком.

Свой асинхронный генератор — `async function*`, внутри можно `await`:
[`05-async-iteration.ts`](examples/05-async-iteration.ts).

> `for...of` спрашивает значения. `for await...of` спрашивает промисы
> значений и ждёт каждый. Механизм один.

### Что такое символ

`Symbol()` — седьмой примитив (урок 1): значение, которое **равно только
самому себе**. Два `Symbol('a')` не равны друг другу. Используют его как
ключ свойства, который гарантированно не совпадёт ни с одним строковым.

Зачем это протоколу. Протокол итератора добавили в язык в 2015 году, когда
кода на JavaScript было уже очень много. Назови метод строкой `'iterator'` —
он совпал бы с полем `iterator` у какого-нибудь старого объекта, и тот
внезапно стал бы «перебираемым» с чужим смыслом. С символом совпадения
быть не может: `{ iterator: 'old' }[Symbol.iterator]` — `undefined`.

Символьные ключи пропускают `Object.keys`, `for...in` и `JSON.stringify` —
поэтому метод и кажется «скрытым». Лежит он не в каждом массиве, а в общем
для всех массивов месте — прототипе (урок про прототипы впереди).

В `wl-e2e` `Symbol` не встречается ни разу. Знать его нужно ровно в объёме
`Symbol.iterator` и `Symbol.asyncIterator`.

### Чем генератор отличается от цикла

Цикл выполняется **целиком**, пока не кончится. Генератор — функция,
которая **отдаёт управление обратно** на каждом `yield`: вызвавший код
получает значение, делает с ним что хочет и сам решает, просить ли
следующее. Выполнение идёт по очереди — шаг генератора, шаг вызвавшего, —
это видно по порядку строк в примере.

Пример с урока — «десять случайных чётных»: сколько случайных чисел
понадобится, заранее неизвестно. Можно написать `while` со счётчиком. Можно
разделить задачу на «бесконечный поток случайных чисел» (генератор) и
«взять первые десять чётных» (цикл с `break`). Во втором случае каждую
половину можно переиспользовать отдельно — ради этого генераторы и пишут.

### Что быстрее

Замер: десять миллионов чисел, взять чётные, удвоить, сложить.

| Способ | мс |
|---|---:|
| `for (let i = 0; …)` | 17 |
| `for...of` | 80 |
| `forEach` | 79 |
| `filter → map → reduce` | **300** |
| `for...of` по генератору | 147 |
| генератор, **первые 10** чётных | 0,0 |

Обычный `for` — самый быстрый. Цепочка из трёх методов — самая медленная:
каждый метод создаёт новый массив. Генератор медленнее `for...of` по
массиву — каждый шаг это новый объект `{ value, done }`, — но если нужно
первые десять, он посчитает только десять.

Для тестов это не важно: один клик в браузере занимает миллисекунды, то есть
столько же, сколько миллион итераций. Выбирать цикл нужно по смыслу
и читаемости.

### Зачем это знать, если в проекте генераторов нет

Писать `function*` в `wl-e2e` почти наверняка не придётся. Что из урока
нужно каждый день:

- **`for...of` против `forEach`** — любой цикл с `await` внутри.
- **Протокол итератора** — объясняет, почему в проекте `Array.from`,
  а спред по DOM-коллекции проходит в редакторе, но не в `yarn typecheck`.
- **`for await`** — семь мест в проекте, и все читают файл.
- **`{ value, done }`** — встретите в типах Playwright и Node.

Генераторы — короткая запись протокола: зная её, вы прочитаете их в чужом
коде и в библиотеках. Этого достаточно.

## Шесть строк, ради которых занятие

1. `for` со счётчиком в проекте — почти всегда **ретрай с потолком**.
   Потолок обязателен: зависший тест хуже упавшего.
2. `for...of` — конструкция языка: работают `break`, `continue`, `await`.
   `forEach` — вызов функции: не работает ни одно из трёх.
3. `for...in` ходит по **ключам**, у массива это **строки**. По массиву —
   `for...of`, по объекту — `Object.entries`.
4. Перебираемость — договорённость: метод `[Symbol.iterator]` возвращает
   объект с `next()`, который отдаёт `{ value, done }`. На ней стоят
   `for...of`, спред, деструктуризация и `Array.from`.
5. `NodeList` и `options` — массивоподобные. Спред по ним проходит
   в редакторе (TypeScript 6.0), но не в `yarn typecheck` (5.9, `lib` без
   `DOM.Iterable`). `Array.from` проходит под обеими — поэтому в проекте он.
6. Генератор — короткая запись того же протокола, и он **ленив**.
   `for await...of` — тот же протокол для промисов, и в проекте он есть.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **итерируемый объект** (iterable) | объект, который умеет отдавать свои элементы по одному. С ним работают `for...of`, спред `[...x]`, деструктуризация и `Array.from` |
| **итератор** (iterator) | объект с методом `next()`, каждый вызов которого отдаёт `{ value, done }`. Когда элементы кончились — `done: true` |
| **протокол итератора** | договорённость: «если у объекта есть метод `[Symbol.iterator]`, возвращающий итератор, то с ним работает `for...of`». Никакой магии внутри цикла нет — он вызывает `next()`, пока не придёт `done: true` |
| **массивоподобный объект** (array-like) | объект с `length` и числовыми индексами, но без методов массива. `NodeList` и `HTMLOptionsCollection` — именно такие: `.map` у них нет, и в проекте их превращают в массив через `Array.from` |
| **генератор** | функция, объявленная через `function*`. При вызове не выполняется, а возвращает итератор: тело идёт до первого `yield`, отдаёт значение и замирает до следующего запроса |
| **ленивое вычисление** | значение считается в момент запроса, а не заранее. Поэтому бесконечная последовательность помещается в память: целиком её никто не создаёт |
