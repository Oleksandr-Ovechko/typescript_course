## Как пользоваться примерами

Каждый пример — исполняемый сценарий. Он собирает свою песочницу
в `/tmp/wl-pw-examples/`: маленькую страницу «записи на класс», свой
сервер, конфиг, повторяющий конфиг `wl-e2e`, и несколько тестов. Потом
выполняет команды и по ходу объясняет, что произошло.

```bash
bash lessons/lesson-11/examples/01-running-and-filtering.sh
cd /tmp/wl-pw-examples/…    # песочница остаётся — заходите и пробуйте сами
```

Ставить ничего не нужно: Playwright берётся из вашего `wl-e2e`
(`~/work/wl-e2e/node_modules`). Если `wl-e2e` лежит в другом месте —
`WL_E2E=/путь/к/wl-e2e bash …`. Staging не нужен: всё идёт локально, за секунды.

## Уточнения к занятию

Места, где на занятии прозвучала неточность. Всё проверено запуском
в песочнице и `git grep` по рабочей ветке.

**1. Репортер по умолчанию — `list`, а не `line`.** `list` печатает строку
на каждый тест. `line` — одну строку, которая перезаписывается. На CI
умолчание — `dot`.

**2. Вьюпорт 1280×800 в конфиге widgets — не умолчание.** Умолчание
`Desktop Chrome` — 1280×720. Высота 800 задана явно, и если её убрать,
окно у всех тестов виджетов станет ниже на 80 пикселей.

**3. `open` у HTML-репортера решает только, открывать ли отчёт
автоматически.** Значений три: `'always'`, `'never'`, `'on-failure'`.
Сам отчёт собирается при **каждом** прогоне, где HTML-репортер указан, —
и при зелёном тоже. Если отчёта нет, значит, HTML-репортера нет в списке
`reporter` того конфига, с которым вы запускали.

**4. У флейки-теста трейс есть — но от прошедшей попытки.** С конфигом
проекта трейс пишется на ретрае. Упал → ретрай прошёл: трейс лежит
в папке `-retry1`, но падения в нём нет. Упал и на ретрае: трейс ретрая
показывает падение. Подробно — [Флейки-тест](#флейки-тест).

**5. Шардирование делит прогон, а не отчёт.** `--shard=1/4` запускает
четверть тестов — на другой машине запускают `2/4` и так далее. Потом
отчёты склеивают `merge-reports`.

**6. `--max-failures N` — «остановить прогон после N падений».**
К ретраям отношения не имеет.

**7. `expect.soft` в проекте используется** — 51 вызов в 34 файлах.
Теги — почти нигде: `@flaky` в пяти тестах.

**8. `error-context.md` пишется только для упавших попыток.** У прошедших
тестов папки в `test-results/` нет вовсе.

**9. Большие тайм-ауты в тестах — не часы, а минуты.** `2_700_000` мс —
45 минут, самый большой в проекте — 80 минут. Самый частый из больших —
30 минут, у 247 тестов.

**10. Проверки `expect(...)` ждут по `expect.timeout` (5 с), а не по
`actionTimeout` (15 с).** `actionTimeout` — для действий: клик, `fill`.

**11. `forbidOnly` работает только на CI** (`!!process.env.CI`). Локально
`test.only` запускается молча — поэтому им и удобно отлаживать.

**12. Мелочи.** Запрет разбирать `trace.zip` записан в агенте
`test-debugger.md`, а не в `RULES.md`. JSON-репортер на `draft` всё-таки
используется — его включает `regression-lane.ts`. Имя видео
`page@<id>.webm` — идентификатор страницы, а не пометка «гость».

## Как запускается тест

### Команда и файлы окружения

В `projects/widgets/package.json`:

```json
"staging": "APP_ENV=${APP_ENV:-staging} yarn playwright test",
"dev": "APP_ENV=demo yarn playwright test",
```

Три слоя:

| Кусок | Что делает |
|---|---|
| `APP_ENV=…` | переменная окружения на одну команду. `${APP_ENV:-staging}` — синтаксис bash «если `APP_ENV` уже задана, оставить, иначе `staging`» |
| `yarn playwright test` | сам Playwright |
| всё, что после `yarn staging` | дописывается в конец: `yarn staging C2358 --project=chromium` → `playwright test C2358 --project=chromium` |

Конфиг читает `APP_ENV` и выбирает файл `config/.env.<имя>`. Прочитать
его помогает библиотека `dotenv`: файл вида `КЛЮЧ=значение` она раскладывает
в `process.env`. Поэтому «на каком стенде идёт тест» решает одна переменная.

Подробнее про сами файлы — в [«Что спрашивали»](#что-лежит-в-файлах-окружения).

### Фильтр по пути, имени и строке

Аргумент после `playwright test` — **регулярное выражение по пути файла**,
а не номер кейса:

```bash
cd ~/work/wl-e2e/projects/widgets
APP_ENV=demo yarn playwright test --list C93                      # Total: 15 tests in 5 files
APP_ENV=demo yarn playwright test --list C93 --project=chromium   # Total: 5 tests in 5 files
```

Два сюрприза в одной команде:

1. `C93` нашло **пять** разных кейсов — `C93309`, `C93310`, `C93515`,
   `C93516`, `C93517`: всё, в пути чего есть эти три символа.
2. Пять файлов дали **пятнадцать** тестов: в конфиге три браузера
   (`chromium`, `firefox`, `webkit`), и без `--project` каждый тест идёт
   в каждом. Поэтому во всех инструкциях проекта стоит `--project=chromium`.

Точная запись для одного кейса — `yarn staging C2358.spec --project=chromium`.

Остальные формы фильтра:

| Запись | Что выберет |
|---|---|
| `tests/booking.spec.ts` | все тесты файла |
| `tests/booking.spec.ts:8` | тест, который **начинается** на строке 8. Строка внутри теста — «No tests found» |
| `regression-run/appointment-widget` | все тесты папки, с подпапками |
| `-g "Yoga"` | тесты, в **имени** которых есть `Yoga` (тоже регулярка) |
| без аргумента | весь проект |

> Сначала `--list`. Он ничего не запускает, только показывает, что
> запустится, — и экономит пятнадцать прогонов в трёх браузерах.

> ⚠️ **`-g` без пути в `wl-e2e` может найти ноль тестов.** Чтобы
> отфильтровать по имени, Playwright сначала загружает **все** спеки
> проекта. Если хоть один падает прямо при загрузке — например, ему
> не хватает переменной в вашем `.env.*.secure`, — в выводе будет его
> стектрейс и `Total: 0 tests`. Решение — сузить путём:
> `yarn dev regression-run/appointment-widget -g "zero-cost" --list`.

Пример — [`01-running-and-filtering.sh`](examples/01-running-and-filtering.sh).

### Воркеры и параллельность

**Воркер** — отдельный процесс со своим браузером. Воркеры не делят ничего:
ни переменных, ни страниц. За параллельность отвечают две настройки, и это
разные вещи:

- `workers` — **потолок**: сколько процессов разрешено поднять. У нас 8.
- `fullyParallel` — **единица параллельности**: отдельный тест (`true`,
  у нас) или целый файл (`false`).

На одном файле из трёх тестов при `workers: 2`:

| `fullyParallel` | Вывод |
|---|---|
| `true` | `Running 3 tests using 2 workers` |
| `false` | `Running 3 tests using 1 worker` |

С `false` тесты одного файла идут в одном воркере по очереди. Воркеров
не больше, чем тестов: `--workers=4` на трёх тестах даст три. Тест
забирает тот воркер, который освободился первым, поэтому номера `1`, `2`,
`3` в выводе раздаются по мере завершения и от прогона к прогону меняются
местами.

Пример — [`02-workers-and-parallel.sh`](examples/02-workers-and-parallel.sh).

### Последовательный режим

```ts
test.describe.configure({ mode: 'serial' });
```

«Тесты этого `describe` — в один воркер, по очереди; упал один — остальные
пропустить». В проекте так написано 380 файлов.

Зачем: тесты делят **состояние** — один бизнес, одна карточка клиента, одни
настройки. Если два теста одновременно пополняют и списывают баланс или
проводят платёж на одну и ту же сумму (платёжка сочтёт второй дублем), они
мешают друг другу. Воркеры ничего не делят, так что при параллельном запуске
второй тест не увидит того, что создал первый.

Цена высокая: параллельности нет, а падение первого теста помечает остальные
как пропущенные. Поэтому общего состояния лучше избегать вовсе:

| Способ | Как |
|---|---|
| Свои данные на каждый тест | создавать клиента в самом тесте или в `beforeEach`; имя — с `workerIndex` или `faker`, чтобы воркеры не столкнулись |
| Фикстура | подготовка и уборка в `test.extend` — так сделан `tracker` в `helpers/fixtures/test.ts` |
| Общее только на чтение | сессия кладётся один раз и переиспользуется (`session-store.ts`) |
| Разные бизнесы | тесты, которые меняют общие настройки, разнести по разным бизнесам — такой план есть у проекта |

Подробно — [документация Playwright про параллельность](https://playwright.dev/docs/test-parallel#serial-mode).

## Конфиг проекта

### Ключи базового конфига

Всё, что Playwright делает без ваших указаний, записано в
`projects/widgets/playwright.config.ts`:

| Ключ | У нас | Что означает |
|---|---|---|
| `testDir` | `'./tests'` | где искать спеки |
| `fullyParallel` | `true` | единица параллельности — тест |
| `forbidOnly` | `!!process.env.CI` | забытый `test.only` валит прогон на CI; локально — нет |
| `retries` | `1` | один повторный запуск упавшего теста |
| `workers` | `8` | потолок процессов (`CI ? 8 : 8` — тернарник, который ничего не выбирает) |
| `reporter` | `[['list'], ['allure-playwright']]` | что печатать и что складывать. В `monolith` третьим — свой TestRail-репортер |
| `use.baseURL` | `WL_UI_BASE_URL` из `.env` | `page.goto('/rs/…')` достраивается от него |
| `use.actionTimeout` | `15_000` | потолок одного действия |
| `use.navigationTimeout` | `15_000` | потолок перехода |
| `use.trace` | `'on-first-retry'` | трейс пишется только на ретрае |
| `timeout` | `60_000` | потолок теста целиком |
| `expect.timeout` | не задан → `5_000` | потолок одной проверки |
| `projects` | chromium, firefox, webkit | три браузера. У chromium явно `viewport: 1280×800` — умолчание было бы 1280×720 |
| `globalSetup` | `'./globalSetup'` | один раз до всех тестов: проверяет, что переменные окружения на месте |

Чего в конфиге нет — и что поэтому не появляется само: `video`,
`screenshot`, HTML-репортер, `storageState`, `webServer`.

Репортеры, которые умеет Playwright:

| Репортер | Что делает | У нас |
|---|---|---|
| `list` | строка на тест | да, умолчание |
| `line` | одна перезаписываемая строка | — |
| `dot` | точка на тест — для больших прогонов | умолчание на CI |
| `html` | сайт с отчётом | в `explorer` — да (`open: 'never'`); в `monolith` и `widgets` — нет, включается своим конфигом или `--reporter=html` |
| `json`, `junit` | файл для других программ | `json` — на `draft`, через `regression-lane.ts` |
| `blob` | сырьё для `merge-reports` | — |
| `github` | аннотации в GitHub Actions | — |
| свой | любой код | `allure-playwright`, TestRail в `monolith` |

### Четыре тайм-аута

От самого маленького к большому:

| Тайм-аут | У нас | Кого ограничивает |
|---|---|---|
| `expect.timeout` | 5 с | одну проверку `expect(...)` |
| `actionTimeout` | 15 с | одно действие: клик, `fill`, `check` |
| `navigationTimeout` | 15 с | один переход: `goto`, ожидание загрузки |
| `timeout` | 60 с | тест целиком |

В сообщении о падении всегда написано, какой сработал: строка `Timeout:`
у `expect` или `Test timeout of … exceeded` у теста.

### Три уровня настроек

Конфиг задаёт умолчание, флаг командной строки его перебивает, а сам тест
перебивает и то и другое:

```bash
pw test tests/booking.spec.ts --retries=0 --workers=1   # флаг сильнее конфига
```

```ts
test.describe.configure({ retries: 2 });   // сильнее --retries=0
test.setTimeout(120_000);                  // сильнее --timeout и конфига
test.slow();                               // утраивает тайм-аут
expect(locator).toBeVisible({ timeout: 30_000 });   // только для этой проверки
```

В проекте `test.setTimeout(` встречается больше пяти тысяч раз — то есть
настоящий тайм-аут теста чаще записан в самом тесте, чем в конфиге.
Прежде чем спорить с конфигом, посмотрите в начало спека.

Пример — [`03-config-levels.sh`](examples/03-config-levels.sh).

### Несколько конфигов

Конфиг по умолчанию — `playwright.config.ts`. Другой выбирается флагом
`-c` (он же `--config=`), и уже он решает, из какой папки брать тесты:

| Файл | Отличия | Команда |
|---|---|---|
| `playwright.config.ts` | база | `yarn staging` |
| `playwright.e2e.config.ts` | `testDir: './end-to-end-tests'`, `workers: 1`, `retries: 0` | `yarn e2e:staging` |
| `playwright.setup.config.ts` | `testDir: './setup-run'`, headed, `expect.timeout: 15_000`, тайм-ауты 30 с, скриншот на падении | `yarn setup:staging` |
| `playwright.probes.config.ts` | `testDir: '.probes'` | пробники Клода |

Все они — `...base` плюс отличия: конфиг — обычный модуль, и его можно
расширить спредом, как любой объект (урок 3).

На `draft` добавились `playwright.probe.config.ts`, `playwright.verify.config.ts`
и общий модуль `helpers/utils/regression-lane.ts`: он читает `WL_LANE`,
`WL_WORKERS`, `WL_LANE_REPORT_DIR`, а у widgets — `WL_TIMEOUT_SCALE`, который
множит тайм-ауты на медленном стенде.

## Что остаётся после падения

### Трейс только у ретрая

С настройками проекта (`retries: 1`, `trace: 'on-first-retry'`) после
упавшего теста в `test-results/`:

```
test-results/booking-book-Pilates-chromium/error-context.md
test-results/booking-book-Pilates-chromium-retry1/error-context.md
test-results/booking-book-Pilates-chromium-retry1/trace.zip
```

- У **первой** попытки трейса нет — только `error-context.md`.
- Трейс — **в папке с `-retry1`** на конце.
- Видео и скриншота нет: проект их не включал.
- У прошедших тестов папок нет.
- `test-results/` **перезаписывается** каждым прогоном — нужное забирайте
  сразу.

`error-context.md` — ошибка, кусок исходника и страница, записанная текстом.
Playwright кладёт его рядом с падением для ИИ: именно этот файл читает
Клод, когда его просят разобрать падение.

Ошибку в терминале читают сверху вниз: **что** проверяли (`toContainText`),
**на чём** (`getByRole('dialog')`), **сколько ждали** (`Timeout: 2000ms`),
**что ждали** (`Booked!`), **что получили** (`Something went wrong`).

Пример — [`04-artifacts-and-report.sh`](examples/04-artifacts-and-report.sh).

### Свой конфиг поверх общего

Общий конфиг трогать нельзя — он у всех. Но можно положить рядом свой:

```ts
// projects/widgets/playwright.my.config.ts
import { defineConfig } from '@playwright/test';
import base from './playwright.config';

export default defineConfig({
  ...base,
  retries: 0,
  reporter: [['list'], ['html', { open: 'on-failure' }]],
  use: {
    ...base.use,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
});
```

| Ключ | Что меняет |
|---|---|
| `retries: 0` | упал — сразу стоп, быстрее при отладке |
| `trace: 'retain-on-failure'` | трейс у **первой же** упавшей попытки |
| `screenshot`, `video` | картинка и видео упавших |
| `html` + `open: 'on-failure'` | упал — отчёт открывается в браузере сам |

Запуск: `yarn staging C2358.spec --project=chromium -c playwright.my.config.ts`.

**Спрятать его от git.** Не через `.gitignore` — он в репозитории, правка
уедет всем. Для личного есть локальный брат `.gitignore` — файл
`.git/info/exclude`: тот же формат, лежит внутри `.git` и никуда не пушится.
Одна строка в нём действует и на все ваши `worktree`:

```bash
echo 'playwright.my.config.ts' >> ~/work/wl-e2e/.git/info/exclude
git status    # файла в списке нет
```

### HTML-отчёт

- Собирается при **каждом** прогоне, где в `reporter` есть `html`, — и при
  зелёном тоже.
- `open` решает только, открывать ли его автоматически: `'always'`,
  `'never'`, `'on-failure'`. Переменная `PLAYWRIGHT_HTML_OPEN` сильнее
  конфига; если не задано ни то, ни другое, действует `'on-failure'`.
- Сам отчёт **не откроется** при любом `open`, если прогон идёт на CI,
  без терминала или его запускает ИИ-агент (Клод): Playwright это
  распознаёт и браузер не поднимает. Открыть руками — `show-report`.
- Сервер отчёта живёт, пока открыт терминал; `Ctrl+C` его гасит, файлы
  остаются. Открыть снова — `yarn playwright show-report`.
- `show-report` открывает **последний** отчёт, какой найдёт. В `monolith`
  и `widgets` HTML-репортера в конфиге нет (в `explorer` — есть), поэтому `yarn report` покажет
  старый отчёт — хоть двухнедельный — или скажет, что отчёта нет. Свежий
  отчёт — только своим конфигом или `--reporter=list,html`.

## Трейс

### Как читать трейс

```bash
yarn playwright show-trace test-results/…-retry1/trace.zip
```

Или кнопкой в HTML-отчёте. Окно состоит из четырёх частей:

| Где | Что | Что в нём смотреть |
|---|---|---|
| Полоса сверху | таймлайн: кадры экрана по времени | где страница стояла, где менялась |
| Слева — Actions | каждое действие с длительностью | самое долгое — первый подозреваемый |
| Центр — Before / Action / After | **снимок DOM** до, во время и после действия | не картинка, а сама страница: кнопка «Open snapshot in a new tab» открывает её вкладкой, там работает F12 |
| Снизу — Call, Log, Console, Network, Errors, Source, Attachments | детали выбранного действия | Log — как Playwright ждал элемент |

Порядок чтения падения:

1. Текст ошибки — что ждали и что получили.
2. **Actions** — какое действие было долгим. Клик длиной в 300 мс — это
   Playwright ждал, пока кнопка появится (**автоожидание**). Вставлять
   перед ним `waitForTimeout` не нужно.
3. **Console** — ошибки, которые написала сама страница.
4. **Network** — ответы сервера. `POST book — 500` значит: тест не виноват,
   отказал сервер.

Селектор подозревать последним.

### Трейс из терминала

С Playwright 1.60 трейс читается без окна — а значит, его может прочитать
и Клод:

```bash
pw trace open test-results/…/trace.zip   # открыть; дальше путь не нужен
pw trace actions                         # список действий с длительностью
pw trace console                         # консоль страницы
pw trace requests                        # сеть
pw trace action 7                        # одно действие подробно, с Log
pw trace close                           # закрыть
```

В агенте `test-debugger.md` в `wl-e2e` записано «не пытайся разбирать
`trace.zip`» — это правило старше версии 1.60.

Пример — [`05-trace-cli.sh`](examples/05-trace-cli.sh).

## Видео

### Фикстурный контекст

**Фикстура** — то, что Playwright готовит тесту сам, до первой строки,
и убирает после: `page`, `context`, `browser` в скобках `async ({ page })`.
Их видно в трейсе строками `Fixture "context"`, `Fixture "page"`.

Ключ `use.video` (`'off'` у нас, `'on'`, `'retain-on-failure'`,
`'on-first-retry'`) действует на **контекст, который создала фикстура**.
Видео ложится в папку теста в `test-results/` или туда, куда указывает
`outputDir`.

### Гостевой контекст

Виджет живёт на сайте клиента, поэтому виджет-тесты открывают **второй**
контекст — гостя, без сессии сотрудника. В проекте это
`openEmbeddedWidgetAsGuest` в `projects/widgets/helpers/components/widgets-navigation.ts`:

```ts
const guestContext = await browser.newContext();
```

Этот контекст создан руками, фикстура о нём не знает — **`use.video` его
не пишет**. На видео будет пустая страница сотрудника и ничего из того,
ради чего тест писался. Отсюда «видео обрывается, когда открывается
другой браузер».

Лечится так: `recordVideo` передают прямо в `newContext`:

```ts
const guestContext = await browser.newContext(
  process.env.WL_VIDEO_DIR ? { recordVideo: { dir: path.resolve(process.env.WL_VIDEO_DIR) } } : {},
);
```

Тогда видео два: фикстурное — в папке теста, гостевое — рядом, файлом
`page@<id>.webm`. Гостевое дописывается в момент `context.close()`, поэтому
контексты надо закрывать. В одно видео их не склеить — это уже работа
для отдельной программы.

В `wl-e2e` для этого есть локальный `playwright.video.config.ts`
(`video: 'on'`, `outputDir` из `WL_VIDEO_DIR`). Две вещи, которые важно
помнить:

- `widgets-navigation.ts` — хелпер Tier-1, и он заморожен. Правка
  с `recordVideo` в нём — только локально: записали видео — откатили
  (`git checkout -- <файл>`) и проверили, что `git diff` по хелперам пуст.
  Если правило для этого файла поменяется, об этом объявят отдельно.
- Записывать только зелёные прогоны: видео пишется и для упавшего теста.

Пример — [`06-video-contexts.sh`](examples/06-video-contexts.sh).

## Флейки-тест

**Флейки-тест** — тест, который на одном и том же коде то проходит, то
падает. С настройками проекта он выглядит так:

```
  ✘  1 … › schedule of a new location (2.1s)
  ✓  2 … › schedule of a new location (retry #1) (390ms)
  1 flaky
exit=0
```

1. **Прогон зелёный** — код возврата 0. Скрипты, пайплайн и TestRail
   увидят «прошёл». Единственный след — слово `flaky`.
2. **Трейс есть, но от прошедшей попытки.** `on-first-retry` пишет его на
   ретрае, а ретрай прошёл. Падения в этом трейсе нет; от упавшей попытки
   остался только `error-context.md`.
3. Если тест упал **и** на ретрае — трейс ретрая показывает падение.

Флейки разбирают **своим конфигом** — `retries: 0`,
`trace: 'retain-on-failure'`: тогда трейс будет у самого падения.

Почему в проекте `retries: 1`: стенд общий, и случайное замедление не должно
валить весь прогон. Цена — флейки прячутся.

Пример — [`07-flaky.sh`](examples/07-flaky.sh).

## Что есть в Playwright, но не у нас

Не список «надо внедрить», а «знать, что такая кнопка есть»:

| Что | У нас | Зачем бы пригодилось |
|---|---|---|
| Теги `{ tag: '@smoke' }` и `--grep @smoke` | `@flaky` в пяти тестах; наборы разделены папками | гонять срез по метке: флейки, медленные, создающие клиентов |
| `projects` + `dependencies` + `storageState` | свои сессии в `session-store.ts` — из-за особенностей логина в монолит | проект `setup` логинится и сохраняет сессию, остальные объявляют его зависимостью |
| `getByTestId` + `testIdAttribute` | 1 вызов против 17 000 `getByRole` | если в вёрстке есть `data-testid`, локатор не ломается от перевода и вёрстки |
| `expect.soft(...)` | 51 вызов; правило **S4** — только для «структурных» проверок, главный сценарий проверяется строго | проверить пять полей и увидеть **все** несовпадения разом |
| `toHaveScreenshot` | 1 | сравнение картинок для вёрстки |
| `--shard=1/4` + `merge-reports` | — | разложить регрессию на несколько машин и склеить отчёт |
| `--only-changed`, `--last-failed`, `--max-failures N`, `-x` | — | быстрые круги при починке: только изменённое, только упавшее, стоп после N падений |

Уже используется, и стоит знать по имени: `test.step` (1 677 вызовов) —
шаги видны в трейсе и отчёте отдельными строками; `expect.poll` (627) —
дождаться меняющегося значения без `waitForTimeout`; `test.info().attach` —
положить свой файл в отчёт.

## Allure

На занятии не успели — разбор здесь и в [`08-allure.sh`](examples/08-allure.sh).

Allure — внешний генератор отчётов, не часть Playwright. В конфиге два
репортера: `list` печатает в терминал, `allure-playwright` пишет файлы
в `allure-results/`:

- по `…-result.json` на **каждую попытку** теста — имя, статус, время,
  шаги `test.step`, метки (браузер, воркер, файл);
- вложения — `error-context.md`, трейс `.zip`.

Это сырьё, а не отчёт. Отчёт собирает отдельная программа:

```bash
yarn allure:report   # allure generate allure-results -o allure-report --clean
yarn allure:open
```

**Allure — Java-программа.** Без установленной Java команда падает
с `JAVA_HOME is not set`. Локально он почти никому не нужен: отчёт собирается
в CI — job `pages` в `.gitlab-ci.yml` копит папку `history` между прогонами
и публикует отчёт.

Зачем он рядом с HTML-отчётом Playwright: **история**. В Allure видно,
что тест падает третий прогон подряд или сломался впервые. HTML-отчёт
показывает только последний прогон.

| Репортер | Для чего |
|---|---|
| `list` | глазами, сейчас |
| HTML | разобрать один прогон |
| Allure | история многих прогонов, CI |
| TestRail (`monolith`) | проставить результаты в TestRail по `[C…]` в имени |

## Что спрашивали на занятии

### Структура папок и TestRail

Папки в проекте — своя структура по разделам продукта
(`regression-run/appointment-widget/…`, `event-widget/…`), и совпадать
с разделами TestRail она не обязана. Связь с TestRail — **через ID кейса**:
он стоит в имени файла (`C2358.spec.ts`) и в названии `describe`
(`[C2358][New Appointment Widget]: …`). TestRail-репортер в `monolith`
находит кейс именно по `[C…]` в названии.

### Что лежит в файлах окружения

У каждого окружения два файла в `config/`:

| Файл | Что внутри | В git |
|---|---|---|
| `.env.<имя>` | публичное: базовые адреса, адреса логина, ID бизнесов | да |
| `.env.<имя>.secure` | секретное: логины, пароли, ключи | **нет** |

Какой из них читать, решает `APP_ENV`: `yarn staging` — это
`APP_ENV=staging`, `yarn dev` — `APP_ENV=demo`, и так далее. Свой стенд —
`APP_ENV=staging-exp3 yarn playwright test …`.

Если `.secure`-файла нет, **ошибки не будет** — конфиг молча поедет без
паролей. Упадёт потом `globalSetup` или сам тест.

### Как выбирать локатор

Все методы `getBy…` — удобные способы найти элемент; то же самое можно
сделать через CSS в `page.locator(...)`. Разница — в устойчивости: CSS
ломается, когда меняется вёрстка, а роль, подпись и текст — нет.

`getByRole` **ждёт так же, как любой локатор** — автоожидание одно для всех.
Если он «не находит», причина почти всегда одна из двух:

- **`name` не совпал.** По умолчанию `name` — подстрока без учёта регистра:
  `{ name: 'book yoga' }` найдёт «Book Yoga». `exact: true` — только точное
  совпадение.
- **У элемента нет такой роли.** `div` с обработчиком клика — не `button`,
  и `getByRole('button')` его не найдёт. Проверить роль — в DevTools,
  вкладка Accessibility, или кнопкой Pick locator в трейсе.
- **`name` подошёл нескольким элементам.** `{ name: 'Book' }` находит
  «Book Yoga», «Book Pilates» и «Book Boxing» — и клик падает **сразу**,
  не дожидаясь тайм-аута: `strict mode violation … resolved to 3 elements`.
  В тексте ошибки Playwright сам подсказывает точные локаторы строками
  `aka getByRole(…)`.

Какие локаторы предпочтительны у нас — правило **S3** в `wl-e2e/CONVENTIONS.md`:
`getByRole`, `getByLabel`, data-атрибуты; XPath запрещён. Клод это правило
читает — это ответ на вопрос «можно ли заставить его выбирать устойчивые
локаторы». Подробно — урок 12.

Пример — [`09-asked-during-lesson.sh`](examples/09-asked-during-lesson.sh).

## Итог занятия

1. `yarn staging X`: `APP_ENV` выбирает `.env`, `X` — **регулярка по пути**,
   без `--project` — **три браузера**. Сначала `--list`.
2. `workers` — потолок, `fullyParallel` — единица параллельности. `serial` —
   для тестов с общим состоянием, и лучше без него.
3. Конфиг — умолчание, флаг сильнее конфига, тест сильнее флага. Четыре
   тайм-аута: 5 → 15 → 15 → 60 с.
4. В проекте трейс только у ретрая — папка `-retry1`. Свой конфиг поверх
   общего, спрятанный через `.git/info/exclude`, даёт трейс, скриншот,
   видео и HTML-отчёт у первой же попытки.
5. Трейс: Actions → Console → Network. Селектор — последний подозреваемый.
6. `use.video` пишет только контекст фикстуры; свой `newContext` — свой
   `recordVideo`.
7. Флейки даёт **зелёный** прогон и трейс **прошедшей** попытки.

## Словарь терминов

| Термин | Что значит |
|--------|------------|
| **воркер** (worker) | отдельный процесс со своим браузером. Воркеры ничего не делят между собой; `workers: 8` в конфиге — не больше восьми одновременно |
| **ретрай** (retry) | повторный запуск упавшего **теста целиком**, с нуля. Не путать с циклом-ретраем из урока 10: тот повторяет одно действие внутри теста |
| **репортер** (reporter) | то, что превращает результаты прогона в вывод: `list` — строки в терминале, `html` — сайт с отчётом, `allure` и TestRail — в проекте |
| **трейс** (trace) | запись прогона: каждое действие, страница до и после, консоль, сеть, исходник. Один файл `trace.zip`, открывается без стенда |
| **снимок DOM** (DOM snapshot) | в трейсе сохраняется не картинка, а сама страница: по ней можно кликать, смотреть HTML в DevTools, подбирать локатор |
| **флейки-тест** (flaky) | тест, который на одном и том же коде то проходит, то падает |
| **фикстура** (fixture) | то, что Playwright готовит тесту сам и убирает после: `page`, `context`, `browser` в скобках `async ({ page })` |
