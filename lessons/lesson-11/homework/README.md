# Домашнее задание к уроку 11

Задания 1–3, 6 и 7 делаются в `wl-e2e`, 4 и 5 — в песочнице примеров
урока. **Против стенда ничего запускать не нужно**, кроме одного своего
кейса в задании 7: всё остальное — `--list`, чтение файлов и уже готовые
результаты прогонов.

Команды в `wl-e2e` запускаются из папки проекта, например:

cd ~/work/wl-e2e/projects/widgets        # или projects/monolith

## 1. Свой конфиг в `wl-e2e`

Создайте рядом с проектным конфигом `playwright.my.config.ts`:

```ts
import { defineConfig } from '@playwright/test';
import base from './playwright.config';

export default defineConfig({
  ...base,
  retries: 0,
  reporter: [['list'], ['html', { open: 'on-failure' }]],
  use: {
    ...base.use,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
});
```

Теперь его надо спрятать от git. **Не через `.gitignore`**: он лежит
в репозитории, и правка в нём уехала бы всем. У `.gitignore` есть
локальный брат — файл `info/exclude` внутри папки `.git`. Формат тот же,
строка на шаблон, но файл никуда не пушится: он только ваш.

```bash
echo 'playwright.my.config.ts' >> "$(git rev-parse --git-common-dir)/info/exclude"
git status --short          # вашего конфига в списке быть не должно
```

Почему `git rev-parse --git-common-dir`, а не просто `.git/info/exclude`:
в `worktree` (урок 9) `.git` — это **файл**, а не папка, и путь `.git/info/…`
там не работает. Команда выше печатает настоящую папку `.git` основного
репозитория — и одна строка в её `info/exclude` действует сразу на все
ваши `worktree`.

Проверьте, что Playwright видит конфиг, — без запуска браузера:

```bash
APP_ENV=demo yarn playwright test --list C2358.spec --project=chromium -c playwright.my.config.ts | tail -1
```

Должно напечатать `Total: 1 test in 1 file` (для `widgets`; в `monolith`
возьмите любой свой кейс).

**Готово, когда** прислан вывод `git status --short` (конфига в нём нет)
и строка `Total:` из команды выше. Когда в следующий раз ваш кейс упадёт
с этим конфигом, HTML-отчёт откроется сам — это и есть «сразу лог при
падении».

## 2. Разобрать падение по трейсу

Возьмите любой упавший кейс из своей очереди — прогон, который у вас уже
был. С конфигом проекта трейс пишется **только на ретрае**, поэтому ищите
его в папке с `-retry1` на конце:

```bash
find test-results -name trace.zip
```

Если трейса нет — у прогона не было ретрая: папки `-retry1` нет вовсе.
Так бывает, когда кейс гоняли e2e-конфигом (там `retries: 0`) или
с флагом `--retries=0`. Тогда перезапустите кейс своим конфигом из
задания 1: с ним трейс пишется у первой же упавшей попытки.

Дальше — трейс в терминале:

```bash
yarn playwright trace open test-results/<папка>-retry1/trace.zip
yarn playwright trace actions
yarn playwright trace console
yarn playwright trace requests
yarn playwright trace close
```

Ответьте на три вопроса, каждый ответ — строкой из вывода:

1. Какое действие самое долгое и почему оно столько длилось?
2. Есть ли в `console` ошибки страницы (`[browser] error`)?
3. Есть ли в `requests` ответы 4xx или 5xx?

И четвёртый, без строки: **где настоящая причина падения** — в тесте,
в селекторе или на стороне сервера?

## 3. Посчитать фильтр

Аргумент после `yarn playwright test` — регулярное выражение по пути
файла, а не номер кейса. Для трёх своих кейсов запустите:

```bash
APP_ENV=demo yarn playwright test --list C2358 | tail -1
APP_ENV=demo yarn playwright test --list C2358 --project=chromium | tail -1
```

Сведите в таблицу: кейс · без `--project` · с `--project=chromium`.

Для ориентира — `C2358` в `widgets`:

```
Total: 3 tests in 1 file        ← три браузера
Total: 1 test in 1 file         ← только chromium
```

Если у какого-то кейса «файлов» больше одного — регулярка зацепила чужие
(как `C93` цепляет `C93309`, `C93515`…). Запишите, как сделать фильтр
точным: `C2358.spec` — после номера сразу `.spec`, и `C23581` уже
не подходит.

## 4. Флейки в песочнице

Запустите пример флейки-теста:

```bash
bash lessons/lesson-11/examples/07-flaky.sh
```

Скрипт гоняет один и тот же тест дважды: с конфигом проекта
(`retries: 1`, `trace: 'on-first-retry'`) и со своим (`retries: 0`,
`trace: 'retain-on-failure'`). После каждого прогона он печатает
содержимое `test-results`.

Ответьте:

1. С конфигом проекта прогон зелёный или красный? Какой код выхода?
2. Трейс от какой попытки сохранился — упавшей или прошедшей? Есть ли
   в нём падение?
3. Что изменилось со своим конфигом — и почему теперь трейс есть
   у падения?

**Готово, когда** присланы оба списка файлов и три ответа. Не принимается
«потому что ретрай»: нужно назвать, какая настройка решила, что трейс
пишется и что он хранится.

## 5. Видео двух контекстов

Запустите пример:

```bash
bash lessons/lesson-11/examples/06-video-contexts.sh
```

Один и тот же тест записывается дважды: без переменной `WL_VIDEO_DIR`
получается один файл, с ней — два. Посмотрите оба видео и найдите на
втором момент клика по «Book Yoga».

Теперь найдите то же самое в проекте. Гостевые контексты виджет-тестов
создаются в общем хелпере:

```bash
git -C ~/work/wl-e2e grep -n 'browser.newContext' origin/draft -- projects/widgets/helpers/components/widgets-navigation.ts
```

Вызовов два: в `openEmbeddedWidgetAsGuest` — `browser.newContext(contextOptions)`,
в `openScheduleWidgetAsGuest` — `browser.newContext()` без параметров. Номера
строк возьмите из вывода: при правках хелпера они сдвигаются.

Ответьте своими словами: **почему `use.video` из конфига не записывает
эти контексты** и что нужно передать в `newContext`, чтобы записал. Слово
«фикстура» в ответе обязательно.

> ⚠️ `widgets-navigation.ts` — общий хелпер (Tier-1), он заморожен (A9).
> Править его для записи видео не нужно: `openEmbeddedWidgetAsGuest`
> принимает опции контекста четвёртым аргументом — `recordVideo` передают
> туда из своего спека.

## 6. Прочитать свой конфиг

Откройте `playwright.config.ts` своего проекта (`widgets` или `monolith`)
и выпишите четыре тайм-аута со строками, где они заданы:

| Тайм-аут | Значение | Строка |
|---|---|---|
| `expect.timeout` | | |
| `use.actionTimeout` | | |
| `use.navigationTimeout` | | |
| `timeout` | | |

Если значения обёрнуты в `scaledTimeout(...)` (так в `widgets`), — что эта
функция делает (`helpers/utils/timeout-scale.ts`) и при каком условии
значение будет другим? Задан ли в вашем конфиге `expect.timeout` (в `widgets`
задан, в `monolith` на `test-generation` — нет)? Если не задан — какое
значение действует и откуда оно берётся?

Какой тайм-аут сработает, если:

1. `expect(button).toBeVisible()` — кнопка так и не появилась;
2. `page.goto(...)` — страница не открылась;
3. тест целиком идёт слишком долго, хотя каждое действие укладывается.

И вопрос про вьюпорт. В `projects/widgets/playwright.config.ts` у проекта
`chromium` стоит `viewport: { width: 1280, height: 800 }`. На уроке
прозвучало, что это разрешение по умолчанию и строку можно удалить.
Проверьте:

```bash
cd ~/work/wl-e2e && node -e "const {devices}=require('@playwright/test'); console.log(devices['Desktop Chrome'].viewport)"
```

Что изменится у виджет-тестов, если строку убрать? И почему в `monolith`
у `chromium` такой строки нет — что там за размер окна?

## 7. Заменить один локатор

Правило проекта — **S3** в `RULES.md` (раздел 5): семантические локаторы — `getByRole`, `getByLabel`,
data-атрибуты; без XPath, без `nth-child`, без слепых `.first()`/`.last()`.
Порядок предпочтения расписан в `projects/widgets/.claude/agents/code-generator.md`,
раздел «Locator Strategy (priority order)»: `getByRole` → `getByText` →
`getByPlaceholder` → `page.locator(css)` — последним, когда семантические
не работают.

Найдите в своём кейсе CSS-локатор. В спеках их нет (правило A2 — только
вызовы хелперов), ищите в `C{id}.helpers.ts` рядом со спеком:

```bash
git -C ~/work/wl-e2e grep -n "page.locator('" -- 'projects/widgets/tests/**/C<ваш-номер>.helpers.ts'
```

Выберите один и замените на `getByRole` / `getByLabel` / `getByPlaceholder`.
Имя для `getByRole` берите из снимка страницы, а не на глаз: откройте трейс
кейса, на нужном шаге — кнопка **Pick locator** над снимком, она покажет,
как Playwright видит элемент.

Меняйте **только свой `C{id}.helpers.ts`** (Tier-2, правится свободно).
Общие хелперы в `helpers/**` заморожены.

Запустите кейс:

```bash
yarn staging C<номер>.spec --project=chromium
```

**Готово, когда** присланы старый локатор, новый и результат прогона.
Если новый не сработал — это тоже результат: пришлите ошибку, разберём
на уроке 12, где подбор локаторов — главная тема.
